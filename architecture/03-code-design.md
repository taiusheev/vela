# Code design

2026-09-22. How the code is organised, the rules every package follows, and the public API of each package. It turns `02-technical-architecture-v2.md` into buildable units and is the contract parallel work is built against. When code and this document disagree, fix one of them in the same change.

## 1. Package map

```
contracts ◄── copy ◄── core ◄──────────────┐
    ▲                                       │
    ├── db                                  │
    ├── adapters                            │
    └── ai                                  │
                                            │
services ── depends on ── contracts · copy · core · db · adapters · ai (through ports)
    ▲
worker ── wires Cloudflare bindings into services' ports; owns HTTP, the Durable Object, queues, cron;
           deployed as two Workers: the pilot Worker `vela` and the admin Worker `vela-admin` (§9, ADR-26)
```

| Package | Owns | Must not |
|---|---|---|
| `@vela/contracts` | Domain tuples and schemas, shared API wire schemas (`src/api.ts`, API contract §11), the channel adapter contract, event names | Contain logic beyond validation |
| `@vela/copy` | Every user-facing messenger string in `en` and `zh-TW`, and `t()` | Know about channels, the database, or time |
| `@vela/core` | Pure functions: local time, the exchange state machine, the daily schedule decision, ask selection, arrival and weekly read rendering, button codec, idempotency keys, tuning, parent commands, turns | Perform I/O, read the clock, generate ids, or import Node or Workers APIs |
| `@vela/db` | The Drizzle schema (source of truth for the data model), migrations, database clients, the PGlite test helper | Contain business queries (those live in services) |
| `@vela/adapters` | One folder per channel implementing `ChannelAdapter`; recorded fixtures | Touch the database, AI, or scheduler |
| `@vela/ai` | Claude calls with versioned prompts and structured outputs, the `Ai` that calls nothing while AI is off, speech-to-text, cost accounting, fakes | Persist anything, read the clock for business decisions |
| `@vela/services` | Application services: scheduling ticks, the outbound gateway, inbound flows, the AI pipeline, jobs | Import Cloudflare APIs; everything platform-specific arrives through ports |
| `@vela/worker` | Hono routes, the `MemberScheduler` and `ReconcileHeartbeat` Durable Objects, queue consumers, cron, bindings, the privacy notice pages, `/healthz`; the two Workers' configurations; the environment setup script | Contain business logic |
| `@vela/app` | The family app (Expo, `apps/app`): the screens of spec §14.1, the Candle & Ink tokens, the light glyph, and the client that talks to the API | Reach the database, or hold a rule the API should enforce |

Dependency direction is enforced by `package.json` dependencies: a package can only import what it declares.

## 2. Rules for all code

**TypeScript.** TypeScript 7, `strict`, `noUncheckedIndexedAccess`, no `any` (use `unknown` and narrow), no non-null assertions, `import type` for types, relative imports with the `.ts` extension, named exports only (default exports only where a platform requires them: the two Workers' entry modules and config files). Exported functions declare their return types.

**Runtime neutrality.** Runtime code in `contracts`, `copy`, `core`, `adapters`, `ai`, and `services` uses only web-standard APIs available in both Cloudflare Workers and Node 24 (`fetch`, `Request`, `Response`, `Headers`, `URL`, `crypto.subtle`, `TextEncoder`, `Intl`). Biome rejects `node:` imports outside tests, test helpers, configs, and scripts.

**Time.** Core never reads the clock; it receives `now: Date`. Services read time only through the `Clock` port. All instants are `Date` in UTC; local calendar values are `LocalDate` (`YYYY-MM-DD`) and `LocalTime` (`HH:MM`) strings interpreted in an IANA zone.

**Ids.** Row ids come from the database (`uuidv7()` defaults, Postgres 18). Code does not invent ids.

**Errors.** Expected domain failures are values or typed errors (`IllegalTransitionError`, `ChannelSendError`, `VelaError` with a `code`). Unexpected failures throw and are logged by the worker. Never swallow an error without logging it.

**Logging.** Services log through the `Logger` port with an event name and flat fields; never log message content, transcripts, phone numbers, or tokens. A caught error is logged as `errorLabel(error)` (§8), never as its message or `String(error)`: a failed query's message lists its parameters, which hold what the family wrote, and a platform's description can repeat what was sent.

**Tests.** Vitest, colocated as `*.test.ts`. Deterministic: fixed clocks, fake adapters, fake AI, PGlite for the database. Each package's `pnpm test` runs in under a minute, except the PGlite-backed suites of `@vela/db` and `@vela/services`, which run with bounded workers and take longer: each test file boots its own PGlite (Postgres compiled to WebAssembly), and each instance reserves a large memory block up front, so `@vela/db` runs its files one at a time (`fileParallelism: false`) and `@vela/services` uses one worker (`maxWorkers: 1`), which keeps the peak at one instance per suite. The root `pnpm test` runs `turbo run test --concurrency=3`, so at most three package suites run at once; do not start a second PGlite-backed suite by hand while one is running. Test names state behaviour ("sends no quiet notice when delivery failed"). PGlite runs one query at a time, so what happens between independent connections is checked by an opt-in suite instead: `packages/services/postgres-tests`, run with `pnpm --filter @vela/services run test:postgres` (add `--pg-bin <PostgreSQL 18 bin directory>` to use local binaries instead of Docker), which creates a disposable PostgreSQL 18 on 127.0.0.1, applies the migration files, and removes it afterwards (§8). It is not part of `pnpm check`.

**Style.** Biome formats and lints; `pnpm check` must pass before every commit. Comments explain why, not what. No dead code, no commented-out code, no TODO without a linked task.

## 3. `@vela/db`

**Schema source of truth.** `src/schema.ts` defines every table with Drizzle. `architecture/schema.sql` is generated from it by `pnpm --filter @vela/db export-sql` and is never edited by hand. CHECK constraints for enumerated columns are generated from the tuples in `@vela/contracts`, so a value added to a tuple reaches the database through a migration. Staging is migrated and in use as of 21 September 2026: the applied initial migration is immutable. Future structural changes append a migration, following the expand-then-contract release rule; never delete or regenerate the applied migration history. Regenerate `architecture/schema.sql` in the same change when the database structure changes. Moving `SUBSCRIPTION_STATUSES` into the shared contracts changes only its source location: the tuple, column and CHECK are unchanged, so that move creates no migration.

**Account linking migration (23 September 2026, not deployed).** `0002_account_linking` adds the 36th table, `account_link_challenges`: the owning user, the hash of the app session that opened it, the family, member, channel link and Telegram identity hash it binds once a code is issued, the code's hash, an attempt count, and the created, expiry, completed and invalidated times. Checks hold each hash to 64 hex characters, attempts to five, the binding to all-or-nothing, the state to one of unbound, pending, completed or invalidated, and the expiry to at most fifteen minutes after creation; every foreign key cascades. The same migration recreates `events_name_check` with `account_linked`.

**API receipt migration (22 September 2026, not deployed).** `0001_api_request_receipts` adds the 35th table without changing `0000_init`: actor/key/request SHA-256 hashes, bounded-lifetime timestamps, optional family/member cascade scopes, and the saved JSON response envelope. A unique actor/key pair coordinates callers; checks constrain hashes, a positive expiry window of at most 24 hours, result shape and member/family scope presence. Schema tests cover the new constraints, cascades and reset coverage. Apply this incremental migration before deploying the updated retention job; neither environment has received it during local implementation.

**Changes from the reference schema** (`architecture/schema.sql` as first drafted):

1. Primary keys default to Postgres 18's native `uuidv7()`; no custom function.
2. `members.next_arrival_at` becomes `members.next_wake_at` (the reconciliation index).
3. `events` is a plain table with a `bigint` identity key and indexes on `(name, at)` and `(family_id, at)`. Partitioning waits until volume justifies it.
4. `exchanges_one_per_day` becomes `UNIQUE (recipient_id, scheduled_for) WHERE scheduled_for IS NOT NULL AND state <> 'withdrawn'`, so two asks cannot claim the same morning even before scheduling.
5. `exchanges.delivery_failed_at timestamptz`.
6. `families.language` (the family group's language, default `en`).
7. New `family_channels (id, family_id, channel, conversation_id, kind CHECK in ('private','group'), linked_by_member_id NULL, linked_at, unlinked_at, linked_text_sha256 NOT NULL (the SHA-256 of the `group.linked` text posted at linking))` with a unique index `family_channels_channel_conversation_id_idx` on `(channel, conversation_id) WHERE unlinked_at IS NULL`: the family's group chat on a messenger, re-linkable while history rows stay. Nothing in the schema limits a family to one linked group; services refuse a second.
8. New `message_refs (channel, conversation_id, message_id, family_id, exchange_id NULL, quiet_event_id NULL, purpose, created_at, PRIMARY KEY (channel, conversation_id, message_id))` with `purpose` in `arrival, repeat, turn_prompt, answer_post, quiet_notice, consent, ask_confirmation`: maps a platform message to what it was about, so replies and button taps resolve.
9. New `onboarding_sessions (channel, conversation_id, external_user_id, step, data jsonb, created_at, updated_at, expires_at, PRIMARY KEY (channel, conversation_id))`.
10. `replies.channel`, `replies.external_id` with a unique index on `(channel, external_id) WHERE external_id IS NOT NULL`; reactions unique on `(exchange_id, member_id, kind) WHERE kind IN ('heart','laugh','hug')`. On Telegram, `answers.external_id` and `replies.external_id` are `<conversation_id>:<message_id>`, because Telegram message ids are unique only within one chat.
11. `quiet_events.last_notified_at`, `quiet_events.notify_count integer NOT NULL DEFAULT 0`, `quiet_events.notified_member_ids uuid[] NOT NULL DEFAULT '{}'`.
12. `outbound.exchange_id uuid NULL` (FK, on delete set null) and `outbound.conversation_id text NOT NULL`; the `kind` CHECK and the budget index use `OUTBOUND_KINDS` and `BUDGETED_OUTBOUND_KINDS`.
13. `turns.prompt_message_id text`; `turns.holder_id` nullable (`ON DELETE SET NULL`), because a prompt open to anyone has no holder.
14. `metrics_daily.family_id` and `member_id` are `NOT NULL`.
15. `members.light_starts_on date` (the first local date arrivals may be delivered).
16. `message_refs.member_id uuid NULL` (`ON DELETE CASCADE`) and `message_refs.local_date date NULL` (the recipient and date a turn prompt is about).
17. `media`: `storage_key`, `mime`, and `bytes` nullable (a received file is known by its provider id before download, and Telegram photos carry no MIME type); `channel`, `provider_file_id`, `provider_unique_id`; `CHECK media_storage_key_or_provider_file_id_check` (a row needs a storage key or a provider file id); `CHECK media_provider_unique_id_channel_check` (a provider unique id needs the channel that issued it); a unique index `media_family_id_channel_provider_unique_id_idx` on `(family_id, channel, provider_unique_id) WHERE provider_unique_id IS NOT NULL`, so a file forwarded again inside one family reuses its row and another family records its own.
18. Channel columns carry CHECKs from `CHANNELS`, `events.name` from `EVENT_NAMES`; media references use `ON DELETE SET NULL`. `exchanges.media_ids` and `exchanges.options` hold media ids without a foreign key; retention removes a deleted id from both.
19. Member references say what a row means once the member is deleted (30 days after leaving). `ON DELETE SET NULL` where the row only credits the member with an act: `exchanges.asker_id`, `media.uploaded_by`, `quiet_events.resolved_by`, `away_periods.set_by`, `stories.asked_by`, `turns.holder_id`, `invites.accepted_by`, and the new `family_channels.linked_by_member_id`. `ON DELETE CASCADE` where the row exists only because of the member: `invites.invited_by`, `invites.for_member_id`, `outbound.actor_id` (a `nearby_ask` whose actor was set null would break the actor CHECK). A null `asker_id` means Vela only when the exchange type is `hello`.
20. `answers.processing_attempts smallint NOT NULL DEFAULT 0`: services increment it when media ingestion or understanding starts, so `reconcile` can re-run an answer that was never understood and stop after the third attempt (§8).
21. `weekly_reads.sent_lines jsonb NULL`, `weekly_reads.sent_suggestion text NULL`, and `weekly_reads.sent_at timestamptz NULL`, with `CHECK weekly_reads_sent_lines_sent_suggestion_sent_at_check` (all three null or all three set): the lines and the suggestion as the founder sent them (`sent_suggestion` is `''` when the founder removed it). `weekly_reads.lines` and `sent_lines` hold one string per line (`string[]`, the `ai.weeklyRead` output shape, zero to four lines); `lines` and `suggestion` stay as the model wrote them, so prompt versions can be compared. `weekly_reads.stats` is `{answered_days, counted_days, hello_mornings, family_asks, usual_time, drift_min, topics[] (people, places, plans and dates mentioned on two or more counted days; never `mentions.health`), voice_len_drift}`; the first four are the counts `renderWeeklyRead` writes for organisers (§5), never the model.
22. `admin_access_log.member_id uuid NULL` with no foreign key (the log outlives members) and `admin_access_log.action text NOT NULL` with `CHECK admin_access_log_action_check` from `ADMIN_ACTIONS`; `what` names the page or a detail of the action and never holds message content.
23. `consents` keeps a proof of consent or decline after the person's data is deleted (2026-09-17, L5 and L6, ADR-28):
    - `member_id` and `contact_id` are `ON DELETE SET NULL` (they were `CASCADE`).
    - `subject_ref text NOT NULL`: `member:<member id>` or `contact:<contact id>`, written at insert and never changed. `CHECK consents_subject_ref_check`: it matches `^(member|contact):` followed by a lowercase uuid, and while `member_id` is set it equals `'member:' || member_id::text`, and while `contact_id` is set it equals `'contact:' || contact_id::text` (so at most one of the two is set).
    - `answer text NOT NULL`, with no default, from `CONSENT_ANSWERS` (`yes`, `no`; `CHECK consents_answer_check`): a decline is a row, not a missing one. `CHECK consents_withdrawn_at_check`: `withdrawn_at IS NULL OR answer = 'yes'`.
    - `subject_deleted_at timestamptz NULL`: when the member or contact was deleted and `evidence` was cut to the proof keys. `CHECK consents_subject_deleted_check`: `member_id IS NOT NULL OR contact_id IS NOT NULL OR (subject_deleted_at IS NOT NULL AND evidence - 'chat_id' - 'message_id' - 'text_sha256' - 'recorded_by' = '{}'::jsonb)`. Postgres checks it on the update a foreign key's `SET NULL` makes, so deleting a member or contact whose consent rows were not forgotten first fails.
    - `kind` gains `health_words` through `CONSENT_KINDS`. Index `consents_subject_ref_idx` on `subject_ref`.
    - `evidence`: for a tap on her consent messages, `{ chat_id, message_id, params, text_sha256 }`; for an "I've read it" tap, `{ chat_id, message_id, text_sha256 }` with the hash from `family_channels.linked_text_sha256` (§8, `proofs.ts`); for a row the founder records, the founder's fields and `recorded_by: "founder"`; once the subject is deleted, only `chat_id`, `message_id`, `text_sha256`, and `recorded_by`, where present.
24. `nearby_contacts.phone text NULL` (it was `NOT NULL`), with `CHECK nearby_contacts_phone_consented_check`: `(phone IS NOT NULL) = (consented_at IS NOT NULL AND declined_at IS NULL)`. A contact's number is stored exactly while their yes stands: setup stores names, a yes brings the number, and a no clears it (2026-09-17, L8).
25. `deletions`: `CHECK deletions_content_hash_check`: `content_hash = encode(sha256(convert_to(object_type || ':' || object_id::text, 'UTF8')), 'hex')`. A deletion proof is the hash of what was deleted and its id, never of a phone number, a storage key, or any other value the row held (2026-09-17, L4).

Everything else in the reference schema stays, including tables later sprints use.

**Exports.**

```ts
// @vela/db
export * from "./schema.ts";                    // tables and relations
export type VelaDatabase;                        // PgDatabase<…, typeof schema>, accepted by services
export type VelaTransaction;                     // the transaction type passed to db.transaction callbacks
export function connectDatabase(connectionString: string): Promise<{ db: VelaDatabase; close(): Promise<void> }>;  // node-postgres; used by both Workers through Hyperdrive and by scripts
// @vela/db/testing
export function createTestDatabase(): Promise<{ db: VelaDatabase; reset(): Promise<void>; close(): Promise<void> }>;  // in-memory PGlite with migrations applied
```

Row types are `typeof table.$inferSelect` and `$inferInsert`, re-exported with friendly names (`Member`, `NewMember`, …).

**Scripts.** `generate` (Drizzle Kit), `export-sql` (writes `architecture/schema.sql`), `migrate` (applies migrations to `DATABASE_URL`), `dev-db` (a persistent PGlite in `.pglite/` served over the Postgres wire protocol on port 54320 for `wrangler dev`).

**Tests.** Migrations apply cleanly to PGlite; every primary key defaults to `uuidv7()` and is named `<table>_pkey`; each invariant is proven by a failing insert: one exchange per recipient per date, the budget index per kind, the `nearby_ask` actor check, answer and reply webhook dedup (and the same Telegram message id in two chats kept apart), one quiet event per exchange, media dedup per family and channel, one linked row per conversation, a weekly read's sent lines, suggestion, and time written together, an admin log entry without its action, a consent without its answer, with a `subject_ref` that does not name its member or contact, or withdrawn on a `no`, a nearby contact's number without a standing yes and a standing yes without a number, a deletion proof that is not the hash of its type and id, and CHECK constraints rejecting unknown enum values (with a test that every CHECK in the database is covered). Deleting a member who left keeps the family's rows and drops the rows that existed only for them; deleting a media row sets every foreign key to it null; deleting a member or a contact fails while a consent row about them is unforgotten, and succeeds once it is forgotten, leaving the row with both references null.

## 4. `@vela/copy`

```ts
export type MessageKey = keyof typeof en;
export function t(lang: Lang, key: MessageKey, params?: Record<string, string | number>): string;
export const catalogs: Record<"en" | "zh-TW", Record<MessageKey, string>>;
```

Placeholders are `{name}`. Languages without a catalog fall back to English. Tests assert every key exists in every catalog, every placeholder in English exists in each translation and no extra ones do, `t()` throws on a missing parameter, and no string uses a gendered pronoun for the kept-light member (the product never assumes gender; use the name). They also pin the parameters services pass for the keys changed on 2026-09-14, keep every `admin.*` key to the parameters `family`, `link`, and `name` (the admin conversation never carries what the family wrote, ADR-21), set `{link}` and `{notice}` apart with whitespace in every language, and hold the Traditional Chinese spacing rules (Latin text, digits, and Latin placeholders are spaced from Chinese characters; name placeholders are not). They hold each language to the weekly read's name in its privacy notice ("weekly read" in English, 每週小記 in Traditional Chinese) and require the nearby step to tell the organiser to ask the contact themselves, never to say that Vela asks, and never to ask for a phone number (2026-09-17). They pin the parameters services pass for the keys added or changed on 2026-09-17 (`consent.request` takes `organiser` and `notice`, `consent.health_words` `organiser`, `flag.notice_no_words` only `name`, `organiser.invite_again` `name` and `link`, and `group.notice_read` and `onboarding.nearby_no_number` none), so `flag.notice_no_words` can never carry a quote. Each weekly read count has a plural key and a `_one` key: in English the plural key uses the plural noun, the `_one` key the singular ("1 of 1 day", "on 1 morning"), and nothing else differs; in Traditional Chinese, which has one form, the `_one` key repeats the plural key. Traditional Chinese strings carry a file-level note that they await native review.

Services supply values the catalog does not format: `{link}` in `admin.*` keys is `Config.publicBaseUrl` followed by an `/admin/...` path (§9); `{notice}` in `group.linked` is `Config.privacyNoticeUrls[family language]`, and in `consent.request` `Config.privacyNoticeUrls[her language]`; `{organiser}` in `consent.request` and `consent.health_words` is the inviter's display name, or the family name when the inviter is gone; `{link}` in `organiser.invite_again`, as in `onboarding.done`, is `https://t.me/<Config.telegramBotUsername>?start=<token>`; `{date}` in `away.confirmed` is "Sunday 21 September" in English and "9月21日（星期日）" in Traditional Chinese, where it takes no spaces around it; `{contacts}` in `quiet.nearby` lists only contacts with `consented_at` set and `declined_at` null, and the line is left out when there are none. `weekly_read.*` keys are rendered only by `renderWeeklyRead` in `@vela/core` (§5), which supplies their values from `weekly_reads.stats`, her name as the family calls her, and the sent suggestion; only organisers receive them, never the kept-light member (spec §8, §13).

Rules `decideSchedule` implements, each with tests:

- Nothing is due and `nextWakeAt` is `null` unless `lightOn` and `status === "active"`.
- **Arrival**: for today, if today is on or after `startsOn`, `now ≥ zonedInstant(today, arrivalTime)`, not delivered, not failed, and `now < zonedInstant(today, prepareTime)`: `deliver_arrival` with `late = minutesBetween(arrivalInstant, now) > lateNoteAfterMinutes`. After the prepare time the day is skipped (the reconciliation job logs it as missed). Before `startsOn` no arrival is due, and the arrival wake is the one on `startsOn`.
- **Repeat**: delivered, not answered, no repeat, not away that date, on or after `startsOn`, `now ≥ deliveredAt + repeatAfterMinutes`.
- **Quiet**: delivered, not failed, not answered, not away, on or after `startsOn`, no quiet yet, `now ≥ deliveredAt + quietAfterMinutes` → `open_quiet` with `notify` true unless the date is inside the learning period and `now < deliveredAt + learningNotifyMinutes`.
- **Notify quiet**: quiet open, unresolved, not answered, and either never notified with `now ≥ deliveredAt + learningNotifyMinutes`, or `waitUntil` set, later than `lastNotifiedAt`, and `now ≥ waitUntil`.
- Yesterday's repeat and quiet stop once today's arrival is delivered, and are not emitted when today's arrival is delivered in the same decision (her morning and yesterday's "in case you missed it" would otherwise arrive together).
- **Turn prompt**: `turnsEnabled`, tomorrow not prepared, prompt not sent, no ask already scheduled for tomorrow (`askScheduled`), `zonedInstant(today, turnPromptTime) ≤ now < zonedInstant(today, prepareTime)`.
- **Prepare**: tomorrow not prepared and `now ≥ zonedInstant(today, prepareTime)`.
- **Weekly read**: `weekdayOf(today) === weeklyReadWeekday`, today (the week's last day) on or after `startsOn`, `now ≥ zonedInstant(today, weeklyReadTime)`, not done for today.
- `nextWakeAt` is the earliest future instant among every rule's next threshold, strictly after `now`; `null` only when inactive.
- Every rule holds across DST transitions in `America/New_York`, `Europe/Berlin`, `Australia/Lord_Howe` (30-minute shift), and `Asia/Taipei` (no DST).

Known limitations, accepted for the pilot: a `startsOn` more than a day ahead still prepares and prompts the dates before it (consent always sets tomorrow, so no pilot flow produces one); an on-behalf voice note or photo ask without words renders "sent you a voice message" or "sent you a photo" without the child's name (no pilot flow sets `onBehalfOf`).

## 6. `@vela/adapters`

Telegram first, in `src/telegram/`. Exports `createTelegramAdapter({ botToken, webhookSecret, botUsername, fetch?, apiBaseUrl?, now? }): ChannelAdapter` plus setup helpers used by scripts (`setWebhook`, `setMyCommands`, `getMe`, and the `TELEGRAM_ALLOWED_UPDATES` tuple, all from the package root). `createTelegramAdapter` throws on a malformed bot token, a webhook secret that is not 1 to 256 characters of `A–Z a–z 0–9 _ -`, or a `botUsername` that is not 1 to 32 characters of `A–Z a–z 0–9 _` (no `@`: a username given as `@VelaLightBot` would silently drop every addressed command).

- **verify**: constant-time comparison of `X-Telegram-Bot-Api-Secret-Token` with the configured secret.
- **parse**: `message` in private chats and groups (text, `/start <param>`, voice, audio as voice, photo using the largest size, sticker, replies, media groups); `callback_query`; `message_reaction`; `my_chat_member` (private: kicked → `blocked`, member → `unblocked`; group: a move into the chat → `bot_added`, out of it → `bot_removed`, so a promotion yields nothing). Voice, audio, the chosen photo size, and each album photo carry `providerUniqueId` from `file_unique_id`. Content without a richer kind (video, video note, animation, document, location, venue, contact, poll, dice, story, checklist, paid media) yields one `other` event with the caption as text. Service messages: a basic group's upgrade to a supergroup (`migrate_to_chat_id` in the old chat, `migrate_from_chat_id` in the new one) yields `migrated` with the old id as the conversation and the new id as `migratedToConversationId`, possibly twice for one move; `left_chat_member` in a group yields `member_left` with `subject` the person who left and `sender` whoever acted (checked before the sender filter, so a removal by an anonymous admin or a moderation bot is reported), except the bot's own departure, which yields nothing (`my_chat_member` reports it). Other service messages (members joining, pins, title changes), edited messages, channel posts, messages from bots, messages sent on behalf of a chat (`sender_chat`, `is_automatic_forward`), and commands addressed to another bot, in text or caption, yield nothing. A command addressed to this bot keeps its raw text, `@mention` included; services strip it. `eventId` is `tg:<update_id>`.
- **send**: one image → `sendPhoto`; two to ten images → `sendMediaGroup`; audio → `sendVoice`; then `sendMessage` with the text and an inline keyboard, `reply_parameters` when replying, link previews disabled, no `parse_mode` (text is never interpreted as markup).
- **Errors**: 403 → `blocked`; 400 "chat not found" → `not_found`; other 400 → `invalid_request`, and a 400 carrying `parameters.migrate_to_chat_id` (the group was upgraded to a supergroup) also sets `ChannelSendError.migratedToConversationId`; 429 → `rate_limited` with `retry_after`; 5xx and network failures → `unavailable`. - **fetchMedia**: `getFile`, then the file download URL; files over 20 MB are rejected with `invalid_request`.

- **Never throws for provider failures.** A failed call returns `ok: false` with a safe default value (`understand`: summary "answered", no mentions; `flag`: `{ flag: false }`; `chips`: generic chips in her language; `translate`: the original text; `readback` and `hello`: `{ lines: [] }`, and services fall back to deterministic copy and `summariseReplies`; `weekly_read`: no lines and a generic suggestion in the reader's language that states nothing about her week). `@vela/ai` does not depend on `@vela/copy` or `@vela/core`. Programming errors still throw.
- **AI off** (decision X, 2026-09-18). The founder has not approved buying Anthropic credit, and Anthropic has no free tier, so a Worker whose var `AI_PROVIDER` is `off` (§9) runs `createOffAi()` (`src/off.ts`) instead of `createClaudeAi`. It makes no network call, so nothing leaves to a provider. Each call first parses its input with the call's input schema, as every `Ai` does, so input the real client rejects is rejected here too; then it resolves `{ ok: false, value: SAFE_DEFAULTS[call](input), record: null }`. AI being off is not a failure: the outcome carries no `error` and no `AiCallRecord`, because no provider was called. `ok` is false, so every call site already takes its failure path; `record` is null, so code that logs a call must check `isAiOff(outcome)` first, and the compiler finds every such place. `isAiOff` tells an outcome of AI being off from a failed call and from a successful one (§8 has what each call site does). Speech-to-text (`Stt`, Deepgram's free credit) is not affected. The eval provider reports an outcome of AI being off as an error (`<call> not run: AI is off`), never as an output, since no model ran.
- **Routing** (ADR-15): `flag` → `claude-opus-5` (low effort); `understand`, `translate`, `readback`, `weekly_read` → `claude-sonnet-5`; `chips`, `suggest`, `hello` → `claude-haiku-4-5`.
- **Calls** use the official SDK, structured outputs validated against Zod schemas, a cached system prompt, and adaptive thinking where the model supports it; a `refusal` stop reason is handled as a failure. The exact SDK surface follows the bundled Claude API reference, not memory. `createClaudeAi` pins the base URL (`https://api.anthropic.com`), the credential (`authToken: null`), the log level (`warn`, so request bodies carrying family words are never logged), 2 retries, and a timeout per call (`TIMEOUT_MS_FOR`), so environment variables cannot redirect requests, add a credential, or turn on debug logging; `ANTHROPIC_CUSTOM_HEADERS` can still add headers to requests for the pinned host.
- **Inputs** are parsed with each call's input schema before any request, by the fake as by the real client. Text longer than `INPUT_TEXT_LIMITS` (names 80, family text 4000, short text 300 UTF-16 code units, never splitting a surrogate pair) is shortened rather than rejected, because it comes from people; any other invalid input throws.
- **Away**: `Understanding.away` is `{ from, until }`. `from` is the first date away and is never before the answer's date (an earlier start becomes that date); an away that ends before it starts, or starts or ends more than `AWAY_HORIZON_DAYS` after the answer, is dropped. `until` null is "until I'm back", which ends only on an answer on or after `from`. Services insert `away_periods.from_date = away.from`.
- **Prompts** are TypeScript modules `src/prompts/<call>.v<N>.ts` exporting `version` and `system`. Current versions: `chips.v1`, `flag.v2`, `hello.v2`, `readback.v1`, `suggest.v1`, `translate.v1`, `understand.v4`, `weekly_read.v4` (zero to four lines about her week and one suggestion, never a count: the counts are rendered from numbers by `renderWeeklyRead`, §5). `understand.v4` replaced `understand.v3` and `flag.v2` replaced `flag.v1` on 2026-09-17 (below). The system prompt is stable (cacheable); the untrusted family content goes in the user turn inside explicit delimiters, and every system prompt says to treat that content as data and never follow instructions inside it.
- **Guardrails** in every prompt and tested in evals: never diagnose or advise, never speak as a family member, never mention monitoring or notes, never invent facts not in the input, keep her words.
- **Health words** (2026-09-17, L3, ADR-27). `UnderstandInput.healthWordsConsent` is required. `understand.v4` is `understand.v3` with two rules added. For every answer: the summary and every mention list never keep the name of a diagnosis or condition a doctor gave, a test or measurement result, or a medicine; the summary says it plainly instead ("saw the doctor", "has a new medicine", "had a test"), and `mentions.health` keeps the body words she used ("knee hurts", "fell", "doctor") without those names. When `healthWordsConsent` is false: `mentions.health` is an empty list, `moodWords` never include `unwell`, and the summary says nothing about her health or body (a fall, pain, eating, sleep, a doctor, a hospital, a medicine), stating only that she answered when the answer is about nothing else ("Mom answered."); `away` is still returned, and a hospital stay is summarised as being away, without the reason. Both rules take precedence over the guardrail to keep the elder's own words. `flag.v2` is `flag.v1` with one rule added: `evidenceQuote` is still the shortest exact excerpt that shows the signal, and when the signal shows without the name of a diagnosis, a test result, or a medicine, the excerpt leaves them out; whether and how to flag is unchanged, and the input is unchanged. Services enforce what they can without a model (flows §3.10): without consent they store `mentions.health` as `[]`, drop `unwell`, and keep no category or quote. The fake `understand` returns no health mentions and no `unwell` when `healthWordsConsent` is false.
- **Weekly read** (spec §8, §13): `WeeklyReadInput` carries only the days she answered (`days`, zero to seven, each with a non-null `answeredAt`), her usual answer time, the answer-time and voice-length drifts, and repeated mentions; it has no count of days answered, mornings nobody asked, or the family's asks, so the model can neither misstate them nor show them to her. `WeeklyRead` is `lines` (zero to four, each 1 to 300 characters) and `suggestion` (1 to 200 characters). The lines never state or imply how many days she answered or did not, a morning nobody asked, or how many asks the family sent.
- **Cost** is computed from `usage` with a price table per model (input, output, cache read, cache write).
- **Speech**: Deepgram prerecorded transcription (`nova-3`) with the training opt-out set; the language model and parameters verified against Deepgram's current documentation for Traditional Chinese and English. Each request times out after 60 seconds (`STT_TIMEOUT_MS`) and resolves as a failure. Below confidence 0.5 in her language the audio is transcribed again with detection, and the detected transcript replaces hers only when it is in another base language with higher confidence, so a `zh` detection (Simplified) never replaces a `zh-TW` transcript.
- **Evals** in `packages/ai/evals/`: a golden set (50 synthetic cases at first, over-weighted to Taiwanese Mandarin, code-switching, register, borderline and clear health mentions, away detection, prompt injection) with a Promptfoo config that runs only when `ANTHROPIC_API_KEY` is present, and a Vitest test that validates the golden set's shape on every run. `CALL_CHECKS` in `evals/suite.ts` adds checks every case of a call runs after its own: each `weekly_read` case, in English and Traditional Chinese, fails on lines that tally days or mornings, point to a day without an answer, say that nobody asked, or count the family's asks (`notMatches` checks). For the health-words rules (2026-09-17), in `evals/cases/understand.json` and `flag.json`, each in English and in Traditional Chinese: an `understand` case with `healthWordsConsent` false whose answer mentions a fall or pain checks that `mentions.health` equals `[]`, that `moodWords` holds no `unwell`, and that the summary contains none of the answer's health words (`notContains`); an `understand` case with `healthWordsConsent` true whose answer relays a diagnosis, a test result, and a medicine name (in Traditional Chinese, for example 糖尿病, 血糖 180, and 二甲雙胍) checks that neither the summary nor `mentions.health` contains them while `mentions.health` is not empty; a `flag` case whose answer holds a fall and a medicine name checks that it flags, that `evidenceQuote` is an excerpt of the answer, and that it does not contain the medicine name. Every existing `understand` case gains `"healthWordsConsent": true`.
- **Tests**: prompt registry integrity (versions unique, every call routed), request shape built for each call (recording fake `fetch`), usage-to-cost arithmetic, refusal and network failures return safe defaults, Deepgram response parsing. From 2026-09-18 (`src/off.test.ts`, `src/evals.test.ts`): `createOffAi` answers each of the eight calls with its safe default and no record without calling `fetch`, and rejects an input the real client would reject; `isAiOff` is true only for an outcome of AI being off, never for a failed or a successful call; the eval provider reports AI being off as an error.

**Understanding re-run.** Every 15 minutes (every 5 until 2026-09-18), after the late ticks, `reconcile` re-enqueues answers with `understood_at` null, received between 15 minutes and 24 hours ago, and `processing_attempts` below 3: a voice answer without a transcript to `ingest_answer_media`, anything else to `understand_answer`. Nothing spaces the attempts out: the re-runs come at the first reconciliations after the answer is 15 minutes old, so all of them fall within about 45 minutes of it (ADR-25 and its update of 2026-09-18). When a job ends without a transcript or without `understood_at` and the answer's `processing_attempts` is 3 or more, the founder gets `admin.understand_failed` at once (no content, a link to the family's admin page), keyed by the answer so it goes out once. `reconcile` enqueues the same note under the same key, as a safety net for a job that crashed after counting its attempt, only for answers received 25 to 48 hours ago: until then an attempt could still be running or queued, and stored state cannot tell it from a crash.

**AI off** (decision X, 2026-09-18; §7, §9). When the Workers run `createOffAi`, every AI call resolves `AiOffOutcome`. Each call site takes the path it takes when a call fails, but treats AI being off as a setting, not a failure: it writes no `ai_calls` row, because no call was made, and logs no failure warning. Speech-to-text is not AI in this sense and runs as before. Services never call `ai.hello`, `ai.readback`, or `ai.suggest`: the hello is the copy `arrival.hello`, and the read-back is `summariseReplies` (§5), so the hello and yesterday's replies still reach her unchanged. Call site by call site:

- **Chips** (`arrivals.ts`, `draftChips`): no `chips` row, and no `chips_failed` warning; the question goes out without chips.
- **Understanding** (`pipeline.ts`, `understandAnswer`):
  - Nothing a model returns is stored: no `summary`, `mood_words`, `mentions`, `away_until`, `flag`, or `flag_reason`.
  - Nothing follows from a model: no flag notice to organisers, no `admin.flag`, no away period, no `away.confirmed`.
  - `understood_at` is set on the first run (`settled`: ok, or AI off), so no `understanding_incomplete` warning is logged, `reconcile` never re-runs the answer, and neither the job nor `reconcile` sends `admin.understand_failed`. An answer left not understood by failed attempts before AI was switched off is understood the same way on its next run, and gets no note either.
- **Translation** (`pipeline.ts`, `translated`): nothing is translated, stored, or logged, and no `translation_failed` or `summary_translation_failed` warning is logged. A voice answer's transcript is still posted to the group (`group.answer_transcript`), without a translation. A written answer gets no second post: the answer post already carries her words as she sent them (flows §3.9).
- **Speech-to-text** (`ingestAnswerMedia`): unchanged. Deepgram transcribes her voice, and the call is logged in `ai_calls`. A failed transcription leaves `understood_at` empty, so `reconcile` re-runs the ingestion as before, and an attempt that ends without a transcript at 3 or more still sends `admin.understand_failed`.
- **Weekly read draft** (`jobs.ts`, `draftWeeklyRead`):
  - The draft is the safe default: no lines and a generic suggestion.
  - No `ai_calls` row and no `weekly_read_draft_failed` warning.
  - `weekly_reads.prompt_version` is `ai_off` (`DRAFTED_WITH_AI_OFF`), because no prompt wrote the draft and prompt versions are compared by what they wrote.
  - `weekly_read_drafted` carries `ai_off: true` beside `ok: false`, which tells it from a draft whose call failed.
  - The founder still gets `admin.weekly_read_draft`, and may type the lines on the admin page before Send.
- **Sent weekly read** (`admin.ts`, `sendWeeklyRead`): no translation for her, nothing stored or logged. She reads the lines as they were sent.

What AI being off cannot do well, left as it is rather than given new behaviour:

- **What the family sees.** It is built from summaries (`summariesForHer`), and there are none, so she gets `parent.family_sees_empty` ("Nothing yet…"), followed by the lines of the latest sent weekly read when it has any, although her answers did reach the group. This needs a product decision.
- **Away periods.** They are no longer read from her answers, so repeats and quiet notices go on while she is away unless the founder sets the period on the admin page (`set_away`).
- **The admin overview** counts an answer read while AI was off as understood, since `understood_at` is set. The markers that AI was off are the Workers' `ai_off` log line, `weekly_reads.prompt_version` `ai_off`, and the `ai_off` property of `weekly_read_drafted`.
- **Switching AI on later** does not go back: answers read while it was off keep `understood_at` and are never summarised, flagged, or translated. Nothing reads them again by itself, since `reconcile` re-runs only answers with `understood_at` null received in the last 24 hours.

**Media storage off** (decision M, 2026-09-20; §9). `Deps.media` is `MediaStore | null`, and the pilot Worker builds it from the var `MEDIA_STORAGE` (§9): with `off` there is no bucket and no port, so Vela keeps no copy of a voice note or photo. Nothing else changes for a family: her voice note or photo still lights the light and still reaches the family group, because Telegram carries the file by its own file id, and a voice answer is still transcribed, because the pipeline fetches the audio from the channel and sends it to Deepgram. What is skipped is only the copy into storage. Path by path:

- **The media row** (`asks.ts`, `answers.ts`, flows §3.5 and §3.9) is written by `recordInboundMedia` (`repo.ts`), which reaches no store either way: it records the channel, the provider file id and the provider unique id, with `mime` and `bytes` as the platform gave them and `storage_key` null, which `media_storage_key_or_provider_file_id_check` already allows beside a provider file id. Unchanged.
- **Transcription** (`pipeline.ts`, `ingestAnswerMedia`): `loadAudio` reads the object first only when there is a store and the row already has a storage key. With the store null it fetches the bytes from the channel on every run and stores nothing, so the row keeps the provider file id it arrived with and its `storage_key`, `mime` and `bytes` stay as they were; speech-to-text, its `ai_calls` row, the transcript post, and the understanding job follow as before. A row stored while storage was on is read from the channel too, since nothing can open its object any more.
- **Retention** (`jobs.ts`, `deleteMedia`): with no storage key there is no object to delete, and the `deletions` row, the id's removal from `exchanges.media_ids` and `exchanges.options`, and the delete of the row itself all go as before. A row stored before storage was switched off logs the error `media_object_unreachable` (`mediaId` and `reason`, never the key) and its object stays in the bucket for the founder to delete; only staging can reach that state, since production refuses to start with storage off.

**Admin actions** (flows §3.17 has each action's database effects). **Contention tests on real PostgreSQL** (23 September 2026, API contract §1). `postgres-tests/` holds the drill the API contract asks for before live writes, run through `scripts/test-postgres.ts`; `pnpm test` never picks it up. Covered: identical requests replay one committed mutation; a changed input conflicts without a second mutation; a failed mutation hides and rolls back its writes; disable racing a provision or update leaves a tombstone and no receipts; different keys for one actor authorize in lock order while other actors stay independent; the receipt cap holds under contention and still replays a matching key; a deleted receipt gives `unavailable`; retention keeps a receipt reused at expiry; a scoped mutation rolls back when its family disappears; racing first-run provisioning returns the winning account; a replay is refused once the account is soft-deleted; and a refreshed session does not repeat a mutation. **API replay foundation** (22 September 2026, used by optional isolated account routes, not deployed). `api-idempotency.ts` exports `runApiMutation`, its request/action types, and `ApiIdempotencyError`. **Account linking by proof of the Telegram account** (23 September 2026, API contract §1, no route yet). `account-linking.ts` exports `startAccountLink`, `issueAccountLinkCode` and `completeAccountLink`, and needs only the database, the clock and the random port. A start opens a challenge bound to the hash of the calling session, live for fifteen minutes, and invalidates that owner's other open ones. The code exists only for a private `start` the member sends the bot from their own Telegram account: that step binds the challenge to the member, their family, their channel link and the hash of their Telegram id, and stores the hash of a 22-character code, refusing a member who is not active or paused, one who has left, a deleted family, a blocked link, or a member another account already holds. Start and completion go through `runApiMutation`, so a repeat replays rather than links twice; the Telegram half takes the same actor lock without a receipt. Nothing calls these yet.

- Admin routes (Hono, `src/admin-app.ts`): `GET /` redirects (302) to `/admin`, so the Worker's bare address opens the overview; every other path outside `/admin` (`/webhooks/telegram`, `/healthz`, `/privacy` included) is 404 and builds nothing. The admin pages, server-rendered:
  - `GET /admin`, the overview, shows no family content. It calls `loadAdminOverview` and then `loadFailedOutbound` with the same identity, one after the other on the request's one database connection, and renders a table of every family (the kept-light member's status, time zone, local date, and next wake; today's exchange type and state, delivery, failure, repeat, and answer times; the quiet event; today's answer kinds and whether each was understood or flagged; AI calls and failures over 24 hours), each family linking to its page, and a failed sends section (`#failed-outbound`) with each failed or dropped row's last due time (`queuedAt`), family, kind and outbound id, member id, status, attempts, and `errorCode`, or "No send has failed or been dropped." Never words, summaries, transcripts, flag quotes, or AI outputs.
  - `GET /admin/families/:familyId` shows one family (`loadFamilyPage`) in anchored sections: members (`#members`, with the forms to record a consent, mark a member left, and mark the kept-light member deceased), inviting again (`#invite`, the `create_invite` form, below), consents (`#consents`, each row's kind, answer, text version, language, channel, given, withdrawn, and evidence), nearby contacts (`#contacts`, each contact's name, relation, number or "—", channel, consented, and declined; the `record_contact_consent` form with a Phone field, and the `add_contact` form, below), away periods (`#away`), answers with their summaries (`#answers`), the flagged answers (`#flags`, each row `#flag-<answer id>` with its content-free `flag_reason`), the answers the re-run could not read (`#not-understood`), weekly reads (`#weekly-reads`, each `#weekly-read-<weekly read id>`: the count lines as organisers will read them, not editable, and for a draft a Send form with the lines and the suggestion; for a read already sent, the sent lines and suggestion), AI calls with their outputs (`#ai`), and deletion (`#delete`). A family that does not exist is 404, an address that is not a family id is 400, and neither logs a view. Links in `admin.*` messages point to the family page, `${publicBaseUrl}/admin/families/<family id>`.
  - `POST /admin/families/:familyId/:action`, one HTML form per `ADMIN_ACTIONS` value except `view`, calls the matching `admin.ts` function with `ctx = { admin, familyId }`, so every id in the form must belong to that family, and redirects back to the family page (303) with the result (`done`, `sent`, `already_sent`, `no_organiser`, `budget`) shown as a notice. A form value the page does not offer (a consent kind, a language, a contact's answer) or a missing confirmation is 400 and changes nothing; a refusal from services is 404 (`not_found`), 409 (`illegal_state`, `no_channel_link`), or 400, with its code and no stack trace. `delete_family` requires typing `delete`. `mark_left` requires typing `left` for every member, because for the kept-light member it puts her light out for good; the page sets her form, and that of any member who has consented, apart under its own heading saying so. `mark_deceased` is offered only for a member whose light is on.
  - The forms of 2026-09-17 (L7, L8). `record_contact_consent` has `phone`: the route passes it, or null when empty, and services refuse a yes without it and a no with it. `add_contact` has `name`, `relation`, `channel`, and a "Their yes" group: `phone`, `consentAt` (UTC), `textVersion`, `lang`, `consentChannel`, and `note`. When `phone` is empty the route passes `yes: null` and refuses (400) any other field of the group that is filled; when `phone` is filled every field of the group is required (400 otherwise), so a number never arrives without a yes, and a yes is never dropped. `create_invite` (`#invite`) is offered only for a family without `deleted_at` whose members include no one whose light is on or was consented to: `invitedBy` (the family's organisers), `name`, `address`, `language` (`en`, `zh-TW`), `country` (the onboarding countries' codes and `ZZ` for Other), `timeZone` (typed, an IANA name), `wakeTime` (`HH:MM`), a hidden `replacesMemberId` (the family's never-consented `invited` member the page showed, or empty), and typing `invite` to confirm; the page says that the new link goes to the organiser in their Telegram chat and that an earlier link stops working. A value the form does not offer, a missing confirmation, or a wake time that is not `HH:MM` is 400.
  - Cloudflare Access protects the whole admin Worker, every hostname Cloudflare associates with it (ADR-26), and every `/admin` request also needs a valid Access token in the Worker (`src/access.ts`): the Worker verifies the `Cf-Access-Jwt-Assertion` header, an RS256 JWT, against the keys at `https://<ACCESS_TEAM_DOMAIN>/cdn-cgi/access/certs` (cached for an hour, fetched again for an unknown `kid`), its `aud` (holding `ACCESS_AUD`), `iss` (`https://<ACCESS_TEAM_DOMAIN>`), expiry, and not-before (60 seconds of skew), and takes the `email` claim as the admin identity. Checking the token in the Worker as well means an Access application switched off or misconfigured cannot open the page. A request without a valid token gets 401. A POST must also be same-origin: its `Origin` header must be present and equal the origin of `PUBLIC_BASE_URL`, the admin Worker's own origin (not whatever hostname the request arrived on), because the Access session cookie would otherwise let another site submit a form from the founder's browser; a POST that fails this gets 403. The admin pages send `referrer-policy: same-origin`, not `no-referrer`: under `no-referrer` the Fetch standard gives a form POST the Origin `null`, which this check refuses. Neither refusal calls services, so neither changes nor logs anything. Only when `ENVIRONMENT` is `development`, where nothing sits in front of `wrangler dev`, a request with no token at all passes as the identity `development`.
- Privacy notices (H4 in ADR-26). The pilot Worker serves `plan/materials/pilot/privacy-notice.en.md` and `privacy-notice.zh-TW.md` at `NOTICE_PATHS` (`src/notices.ts`: `/privacy` and `/privacy/zh-TW`), without a Markdown dependency. `scripts/notice-markdown.ts` understands only what the notices use (`#` to `###` headings, paragraphs, `-` and numbered lists, tables, block quotes, `**strong**` and `*emphasis*`, https and mailto links, code spans), escapes every character of text, and throws with the line number on anything else (indented lines, fences, raw HTML, rules, setext headings, `*` or `+` lists, other link targets). `pnpm --filter @vela/worker notices` (`scripts/generate-notices.ts`) writes the committed module `src/notices.generated.ts` (`PRIVACY_NOTICES`, each notice's `title`, `html`, and, from 2026-09-17, `version`: the code span of its "Version `privacy-notice.vN`" line; the generator throws when a notice has no such line or the two notices' versions differ), which is all the Worker serves, and `readConfig` sets `Config.privacyNoticeVersion` from it; `src/notices.test.ts` renders the Markdown again and fails while that module is stale, so CI catches a notice edit that was not regenerated. `noticePage(lang, notice)` (`src/html.ts`) returns a plain page with `lang` set to the notice's language, one narrow column for a phone, no script and no external request (`content-security-policy: default-src 'none'; style-src 'unsafe-inline'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'`), and `cache-control: public, max-age=300`. `unfilledPlaceholders(html)` lists the bracketed text left in a notice, except `[Name]` and `[名字]`, which quote the pause message; any other bracket, new ones included, counts as a blank. Outside development `refuseUnfilledNotices` throws `ConfigError` whose `code` is the notice's file name (`ConfigError:privacy-notice.en.md`) while either notice holds a blank: both pages answer 500, and `createDeps` refuses the same way, so no webhook update, queue job, cron run, or alarm tick runs either. Development serves the notices blanks and all, for the founder to read.
- `MemberScheduler`, exported by the pilot Worker, which alone declares its migration; the admin Worker binds the same class with `script_name` `vela` (`vela-dev` locally), so a wake the admin page asks for lands on the object whose alarm runs the tick. RPC `wakeAt(memberId, at)` stores the member id and sets the alarm no later than `at`: an alarm already set sooner stays, because the tick decides from the data, so an early wake costs one tick that finds nothing due while a later one could lose a wake asked for mid-tick. `wakeAt(memberId, null)` deletes the alarm and all stored state (a member who stopped, left, died, or was deleted keeps nothing in the object). `alarm()` calls `tickMember` with a scheduler port that sets this object's own alarm directly (an RPC to itself would wait on its own lock); a null result deletes the alarm, any other is armed no later than the returned instant. A tick that throws is logged as `scheduler_tick_failed` with `errorLabel` and tried again within a minute. An alarm that fires after the object was cleared does nothing.
- Heartbeat (2026-09-18, decisions W1, W2; ADR-18 update). `ReconcileHeartbeat`, exported by the pilot Worker, is a SQLite-backed Durable Object class declared with its own migration in `wrangler.jsonc` (development, staging, and production) and bound as `RECONCILE_HEARTBEAT`; the admin Worker does not bind it. One instance, reached by a fixed name, stores only the instant of the last successful reconcile, never an id or any content, and it is not a Postgres row, so reading it wakes no database. The pilot Worker's `Heartbeat` port (`createHeartbeat` in `src/heartbeat.ts`, built by `buildDeps`) has the object record the current time, by its own clock, when `reconcile` calls `ping()` at the end of a run; a failed write is logged as `heartbeat_failed` with `errorLabel` and does not fail the run. `GET /healthz` reads the instant (`readHealth`): 200 with `{"status":"ok","lastReconcileAgeSeconds":<whole seconds>}` when it is at most 35 minutes old (`HEARTBEAT_FRESH_SECONDS`), 503 with `{"status":"stale"}` when older, and 503 with `{"status":"no_reconcile_yet"}` when nothing was ever recorded, with `cache-control: no-store`. 35 minutes is two missed 15-minute runs plus five minutes. A cron that stops, a configuration the Worker refuses, or a database it cannot reach all leave the instant to age, which is what the outside watchdog reads: `.github/workflows/watchdog.yml` every 15 minutes checks each environment `.github/watchdog.json` enables and fails, so GitHub emails the founder, when one does not answer 200 with `ok` (W4; `infra/README.md`, section 6). Development answers the same way from its local object.
- Queues, consumed by the pilot Worker only: `vela-outbound` → `deliverOutbound`; `vela-media` → `ingestAnswerMedia`; `vela-understand` → `understandAnswer` (in staging and production the names end in `-staging` or `-production`). The admin Worker only produces onto the outbound queue. One set of deps per batch; a message is acked when its job returns and retried when it throws, logged as `queue_job_failed` with `errorLabel`, and after its `max_retries` it goes to the environment's one dead-letter queue (`vela-dead-letter`, `vela-dead-letter-staging`, `vela-dead-letter-production`). A body that is not a job is logged and acked.
- Cron, on the pilot Worker only: every 15 minutes (`RECONCILE_CRON`, `*/15 * * * *`; every 5 until 2026-09-18, W3) `reconcile` (pending send effects, stranded sends, late ticks, the understanding re-run and the founder's note, then the heartbeat record); nightly at 03:20 UTC `rollupMetrics`, then `applyRetention`. Every run of `reconcile` wakes the database, and Neon's Free plan suspends a project's compute when its monthly compute hours are used, so the interval is 15 minutes; the per-member alarms stay the primary scheduler, and flows §3.15 re-checks each threshold at that interval. A run that throws, building its deps included, is logged as `cron_failed` with the cron and `errorLabel(error)`, and fails with an error whose message is only that label.
- Errors: in either Worker, an unexpected failure in a route answers 500 (so Telegram redelivers a webhook) and is logged as `request_failed` with the path, the method, and `errorLabel(error)` (`requestFailed`, `src/request-errors.ts`); every error the Workers log (`request_failed`, `queue_job_failed`, `scheduler_tick_failed`, `cron_failed`) is logged by its label, never its message.

## 11. Definition of done for code

A change is done when `pnpm check` passes locally and in CI, new behaviour has tests that would fail without it, no rule in §2 is broken, and any change to a contract is reflected here and in the architecture document in the same commit.
