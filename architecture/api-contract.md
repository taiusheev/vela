# API contract, v2

2026-09-26 (written 2026-09-13; §10's health check revised 2026-09-18 to the pilot Worker as built; shared schemas and the unmounted access-control foundation added 2026-09-21; durable mutation receipts added locally 2026-09-22; account linking by proof of the Telegram account, its migration, and the contention drill's findings 2026-09-23; mounted on the pilot Worker under `/v1`, on in development and staging and off in production, 2026-09-25, and deployed to staging the same day (ADR-29); tomorrow's suggestion, written nightly and used by composing, 2026-09-26 (ADR-31), not yet deployed; photos for an ask, uploaded from the app, kept in R2 behind the Worker and uploaded to Telegram at delivery, 2026-09-26 (ADR-33), not yet deployed; push to the app's phones through Expo, with the phone routes and "One moment a day" on `PATCH /v1/me`, built and switched off in every environment, 2026-09-27 (ADR-34), not yet deployed). The contract between the Expo app (and the web admin) and the worker, plus the inbound webhooks. Every endpoint maps to spec v2 (`product/05-product-spec-v2.md`); every request and response is a Zod schema in `packages/contracts`, shared by the worker and the app, so a change breaks the build before it breaks a family.

Conventions: JSON over HTTPS; `Authorization: Bearer <session>`; ids are uuids; times are ISO-8601 with offset; every mutating call accepts an `Idempotency-Key` header and returns the first result on replay; errors are `{error: {code, message, details?}}` with codes `unauthenticated`, `forbidden`, `not_found`, `invalid`, `conflict`, `budget`, `rate_limited`, `internal` (500), `unavailable` (503); pagination by cursor (`?cursor=&limit=`); all text fields are returned in the caller's language with `original` alongside when translated.

### Authentication and family-access foundation (21 September 2026)

Implemented and tested; from 25 September 2026 **served by the pilot Worker under `/v1`** wherever its `API_V1` is `on` (§ "Where the API runs"):

- `apps/worker/src/session.ts` exposes `createClerkSessionVerifier(options)`. Its caller supplies a trusted HTTPS issuer origin, an explicit list of authorized application origins, optional audience, and an explicit native-client opt-in for tokens without `azp`. The pilot Worker supplies the issuer from its var `CLERK_ISSUER`, lists no authorized parties and sets the native-client opt-in, so any request carrying `Origin` is refused. Use one verifier per configured issuer per isolate; do not construct it from request headers or token claims.
- Verification uses the pinned `jose` dependency and only the configured issuer's `/.well-known/jwks.json`: redirects are not followed, key requests time out after 5 seconds, keys are cached for 10 minutes, and unknown key IDs trigger a refresh only after a 30-second cooldown. Token-supplied `jku` and `jwk` do not choose the verification keys. Only an `Authorization: Bearer` token is read; cookies, query parameters and Cloudflare Access headers are not alternatives, even in development.
- The verifier requires RS256, JWT type, a nonblank key ID, issuer, subject, session ID, version 2 and integer `iat`, `nbf`, `exp` claims. Vela accepts at most a 120-second token lifetime and age with 5 seconds of clock skew. Pending or unknown session statuses are rejected; absent `sts` or `active` is accepted. `aud` is checked when configured, because ordinary Clerk session tokens do not require an audience. The result contains only `{authSubject, sessionId}`, never the token, email or claimed family role.
- If `azp` exists it must exactly match an allowed application origin. If the HTTP request includes `Origin`, it must both be allowed and equal the token's `azp`; two allowed origins cannot substitute for each other. Application origins must use HTTPS unless `allowLocalHttpParties` is explicitly true for loopback development origins only (`localhost`, `127.0.0.1`, `[::1]`); the issuer always requires HTTPS. Missing `azp` is refused unless `allowMissingAuthorizedParty` is explicitly true, and is still refused when the request carries an `Origin`. This permits native Expo bearer requests without weakening the default browser policy; it is not device attestation. Invalid tokens return no identity. Key-service or verification infrastructure failures throw `SessionVerificationUnavailable` without token or provider error details, rather than being misreported as a bad login.
- `packages/services/src/api-access.ts` exposes `authorizeFamilyAccess(dbOrTransaction, identity, familyId, requiredRole?)`. It joins `users.auth_subject` to `members.user_id` and the requested family, accepting only a non-deleted account, a non-deleted family, and an active or paused membership with no `left_at`. Pausing the light must not prevent reading the family or resuming it. Invited, left, deceased, Telegram-only/unmapped and cross-family callers receive the same `not_found` result. An eligible member lacking the server-required organiser role receives `forbidden`; a grant contains only the database's user, member and family IDs and role. There is no automatic account creation, email/phone linking or authorization cache.
- `apps/worker/src/api-security.ts` supplies reusable Hono authentication and family-authorization middleware. Authentication runs first; family authorization takes the family ID from the route's `:familyId`, not the body, query or headers. Missing/invalid identity is 401, nonmembership/missing family is 404, and a role refusal is 403, using the public error envelope; protected responses carry `Cache-Control: no-store`. Register the API's error handler through `withApiErrorNoStore(handler)` as well: it forces that header on the handler's returned response, including raw responses from failures inside the authentication middleware itself. The wrapper controls caching, not the error payload; the handler must return sanitized public errors. Operational failures propagate to the API error handler, not to a success or authentication refusal; the isolated read API below now supplies that handler. The middleware is tested in an isolated Hono app only; it exposes no new live route.

**Before production turns the API on** (from 25 September 2026 the configuration turns it on for development and staging, with the development Clerk instance, the online session checker and the admission limits of ADR-29; the items below that remain are still gates for production): configure and smoke-test the real Clerk issuer/client, wire and smoke-test the optional account-write capability and its online session checker, integrate verified lifecycle events and gateway rate limits, among them a write limit shown to act (done 26 September 2026: the write limit is a Durable Object per account, and a burst of signed-in writes on staging was refused after the 20th, where the rate-limit bindings had not acted the day before; § "Where the API runs"), expose the proof-of-ownership account linking that §"Account linking" below now implements, and add the remaining endpoint-specific authorization and consent checks. If production's `AI_PROVIDER` is `anthropic` when its API is turned on (production refuses `off`), the privacy notice must first name "suggest an ask for the family" among Anthropic's purposes: wherever the API is on, the nightly job asks the model to draft tomorrow's suggestion from her recent answers (§ "Tomorrow's suggestion", ADR-31). Production's media bucket must also have the lifecycle rule that deletes objects under `asks/` after 32 days, the backstop for a photo upload whose row was never written (§ "Photos for an ask", ADR-33). Before production's `PUSH_SEND` is turned on, or any real family gets a push anywhere: a privacy notice version, in English and Traditional Chinese, that names Expo, Apple and Google, whose services carry each push's text and every phone's token; Expo's data processing terms found or asked for, and the date Expo's, Apple's and Google's were accepted in `infra/sub-processors.md`; Enhanced Push Security on, with `EXPO_ACCESS_TOKEN` on production's pilot Worker; and `0005_push` on production's database (§ "Push", ADR-34). Membership is not permission to operate on every nested resource: each query must constrain target member/exchange/media IDs to the authorized family. Mutations must recheck authorization and relevant state within their transaction, with locking where concurrent changes require it. Cryptographic verification alone does not check session revocation with Clerk; a revoked session's still-valid JWT can survive until expiry. Sensitive operations need an online session check or a revocation mechanism before exposure. Production and the existing Telegram/admin paths are unchanged.

Clerk references checked for this implementation: [manual verification](https://clerk.com/docs/guides/sessions/manual-jwt-verification), [session claims](https://clerk.com/docs/guides/sessions/session-tokens).

### Where the API runs (25 September 2026, ADR-29)

The pilot Worker `vela` serves every path under `/v1` wherever its `API_V1` is `on`: in development, and in staging at `https://vela.vela-light-staging.workers.dev/v1/…`. Staging has served it since 25 September 2026 (commit `6095ccf`), deployed after the founder's key rotation and staging migrations 0001–0002 (infra/README.md §9a, step 9), and its smoke tests passed: `GET /v1/me` answered 401 `unauthenticated` with no token, with `Bearer not-a-token` and with a well-formed RS256 token no key of the instance signed, `POST /v1/me/provision` and `POST /v1/families` 401 without one, a request carrying `Origin` 401 even with a token, `OPTIONS /v1/me` 404 with no `Access-Control-` header, `HEAD /v1/me` 404, `/v1/nope` 404 JSON and `/v1x` the pilot's 404, and `wrangler tail` showed the `Authorization` header redacted and no log line of the Worker's for the 401s. Neither admission limit was then shown to act there, when both were Workers Rate Limiting bindings: 135 sequential requests and then a burst of 220, 25 at a time, from one address within about two minutes all answered 401, with no 429 and no `api_rate_limit_failed` line, so the binding's `limit()` returned success every time, as a Cloudflare community report of 28 August 2026 describes on workers.dev (community.cloudflare.com/t/953250). From 26 September 2026 the per-account write limit is a Durable Object per account instead (below), which the Worker's tests, run in workerd against the real object, show admitting an account's first 20 writes of a minute and refusing the rest, one after the other or 40 at once, across an eviction of the object; the address limit stays a binding and a best effort. On 26 September 2026 commit `23a4acc` was deployed to staging (`vela` version `ca33d2bf`; `vela-admin` unchanged and not redeployed), and `GET /v1/me` without a token answered 401, not 503, so the configuration check found the binding. With the founder's yes, a throwaway user in the development instance, given a session token through Clerk's Backend API (create a user, a session, then a token, as Clerk's testing guide describes), sent 25 `PATCH /v1/me` one after another from one address: the first 20 answered 404, since the account was never provisioned, so each passed the limit and the live session check and its transaction rolled back, leaving nothing in staging's database, and the next 5 answered 429 `rate_limited`. The user was then deleted. A second run, with another throwaway user after the founder asked for it, sent 30 writes at the same moment: exactly 20 answered 404 and 10 answered 429, and one more sent right after answered 429; that user was deleted too. So the write limit is shown to act on workers.dev, and the write path is shown end to end on staging: the token verified, the live session check answered by Clerk with the rotated key, and a transaction through Hyperdrive (ADR-29, updates of 25 and 26 September 2026). Production's `API_V1` is `off`, so `/v1` answers 404 there and reads no Clerk setting. The API is dispatched before the pilot's routes and checks its own configuration: an unknown `API_V1`; outside development, a `PLACEHOLDER_` value in any variable or secret (the pilot's included, since it means the environment's setup is not finished); a missing or non-https `CLERK_ISSUER` or one with a path; an issuer or `CLERK_SECRET_KEY` of the wrong Clerk instance for the environment (development and staging: `*.clerk.accounts.dev` and `sk_test_`; production: neither, and `sk_live_`); a key without a Clerk secret key's shape; or, outside development, a missing limiter binding (`API_IP_LIMIT` or `ACCOUNT_WRITE_LIMITER`) answers 503 `unavailable` and logs `api_config_refused` with the variable's name only; so does an app that fails to build. Staging requires the secret key, so its writes, the live session check and `POST /v1/families` are always served; development without a key serves reads only. Admission: at most 120 requests a minute per client address (per /64 for IPv6), a Workers Rate Limiting binding checked after the configuration check and the off switch and before the app, and a best effort; and at most 20 writes per account in any 60 seconds, counted in the account's own `AccountWriteLimiter` Durable Object after the body is validated and before the live session check, so a malformed write spends none of the allowance, and a refused one no Clerk call and no database connection. A refused write is not counted: the account's next write is admitted once its oldest counted write is 60 seconds old, however often it retries meanwhile. Either limit answers 429 `rate_limited`, the first with `Retry-After: 60` and the second without one, and neither writes a log line. An address limiter that fails is skipped; a write limiter that fails closes the write with 503 `unavailable`, as a live session check that cannot reach Clerk does, so an account cannot lift its own limit by overloading its object; either failure is logged as `api_rate_limit_failed` with its scope, never with the address or the account. The object keeps only the times of the account's writes within the last 60 seconds, and an alarm clears it within 60 seconds of the account's last write. A request carrying `Origin`, or a token carrying `azp`, is 401; `OPTIONS` is 404 and no `Access-Control-` header is sent. Each request that passes authentication and needs the database opens one connection through the environment's Hyperdrive and closes it before answering. A write's outbound rows are handed to the environment's outbound queue and its wakes to the member's scheduler after the commit. The API has no health route of its own: `GET /v1/me` without a token answering 401 shows it is mounted and configured, which is what the setup script's `check` step asks.

### Account provisioning and read APIs (21 September 2026)

`apps/worker/src/api-app.ts` implements `createApiApp(runtime)`, an isolated Hono app whose default configuration has exactly two read routes: `GET /v1/me` and `GET /v1/families/:familyId/plan`. The pilot Worker has mounted it under `/v1` since 25 September 2026 (§ "Where the API runs"); the admin Worker does not. Its two migrations, `0001_api_request_receipts` and `0002_account_linking`, were applied to staging's database on 25 September 2026, before its deploy, and not to production's (infra/README.md §9a, step 9). Unsupported methods (including HEAD) and unknown paths return 404 without opening the database.

`ApiRuntime` supplies the session verifier, a database-handle factory, the three read/access services and an error logger. Authentication runs before a matched read route opens a database; the request opens one handle and awaits its `close()` in `finally` on success, denial or failure. A cleanup failure logs `api_database_close_failed` with an error label only; it does not overwrite the original response or request error. The API does not construct Telegram, AI or speech ports; the pilot Worker gives it the outbound queue and the member scheduler for what a write leaves after its commit (ADR-29), and the media store for photos from the app (ADR-33, § "Photos for an ask"). The family route uses the family guard, and the read service repeats its access conditions in the data query, so a grant cached earlier in the request is not sufficient. Responses are parsed through the shared schemas, which strip undeclared fields. All responses use `no-store`. The error boundary returns generic JSON: 503 `unavailable` for `SessionVerificationUnavailable`, 500 `internal` for other unexpected failures, including invalid service output. Only `errorLabel(error)` is logged, never the raw error, path, query, token or profile.

- **Explicit provisioning, internal only:** `provisionApiUser(dbOrTransaction, verifiedIdentity, profile)` in `packages/services/src/api-accounts.ts` accepts `ApiAccountProfile`: `{display_name, language, tz}`. The name is trimmed and must contain 1–80 characters; the language and IANA zone use the shared domain schemas. Unknown fields, including identity, role, email, phone and member IDs, are rejected. The subject comes only from the verified identity. An insert conflicts only on `users.auth_subject`: the first profile and UUID win, and repeats or racing calls return that existing live account unchanged. A retained soft-deleted account is not resurrected. Provisioning neither creates a family/membership nor attaches any Telegram member; no GET calls it. The optional HTTP provisioning route below calls the receipt-backed wrapper instead of exposing this low-level helper directly. Concurrent insert/reselect uses PostgreSQL's default READ COMMITTED behavior; callers choosing stronger transaction isolation must handle serialization failures by retrying the whole transaction.
- **`GET /v1/me`:** `loadApiMe` returns `ApiMe`, `{user: {id, display_name, language, tz}, memberships: [{member_id, role, status, family: {id, name, region, plan}}]}`. One SELECT uses the exact subject and excludes deleted accounts, non-active/non-paused or departed memberships, and deleted families. Memberships are ordered by their creation time then ID. An existing account with no eligible membership gets an empty list; an unmapped or deleted account gets 404 `not_found`, with no creation or mutation. Since 27 September 2026 it also carries the account's `one_moment_a_day`, and the route adds `push`, whether this API sends pushes, beside `photos` (§ "Push"). Auth subjects, session IDs, email, phone and other members' private fields are not returned.
- **`GET /v1/families/:familyId/plan`:** `loadApiFamilyPlan` returns `ApiFamilyPlan`, `{family_id, plan, subscriptions: [{member_id, status, trial_ends_at, current_period_end, grace_until}]}`. Ordinary eligible members may read it. The query checks the caller's live membership and account, the family's deletion state, and both the subscription's family and its covered member's family. Only active/paused covered members without a departure time are included. Missing/nonmember/deleted callers share 404. An authorized family with no visible subscription rows gets an empty list, not an invented subscription status. Dates are ISO instants or explicit nulls. These are stored plan/status records, not computed billing entitlements; no trial is started and no expired status is rewritten. Provider, external subscription, payer, currency and price fields stay private.

`SubscriptionStatus` and `SUBSCRIPTION_STATUSES` now live in `@vela/contracts` and the database re-exports the same tuple. Its values and SQL CHECK remain unchanged. Linking an existing channel member goes only through the proof-of-ownership challenge below; neither matching profile text nor guessing a member ID grants membership.

### Opt-in account writes and lifecycle (22 September 2026; served by the pilot Worker, on staging, from 25 September 2026)

Only when `ApiRuntime.writes` is supplied does the isolated API register `POST /v1/me/provision` and `PATCH /v1/me`. That capability requires a clock, the two write services and an online `SessionActivityChecker`. Without it, writes still return 404. The pilot Worker supplies it wherever the API is on and `CLERK_SECRET_KEY` is set: always in staging, which requires the key, and in development when one is given; the admin Worker never serves the API.

- Both paths authenticate the bearer token first, require a valid `Idempotency-Key`, and accept only uncompressed UTF-8 `application/json`. Bodies are streamed with a 4096-byte limit, bounded read count and a 10-second total deadline; declared size never substitutes for counting actual bytes. Malformed key/JSON/schema is 400, unsupported media/encoding is 415, oversized data is 413, and a stalled body is 408. Rejection precedes provider activity checks or database creation. Cancellation is not awaited indefinitely; a cancellation failure logs only its error label.
- `ApiAccountProfile` is the complete first-run body. `ApiAccountPatch` is a strict, nonempty subset of `display_name`, `language`, `tz` and, from 27 September 2026, `one_moment_a_day` (§ "Push"), rejecting explicit undefined fields. Names must be well-formed Unicode without NUL after trimming, at most 80 UTF-16 code units. Both reject identity, role, email, phone, member/family IDs, invite tokens and linking instructions. User-profile changes never change member profiles, schedules, channel links or consent.
- `createClerkSessionActivityChecker({secretKey, fetch?})` in `session.ts` checks `GET https://api.clerk.com/v1/sessions/<sid>` using the configured backend credential, after JWT verification. It validates the session-ID path segment, never follows redirects, never caches successful activity, uses a five-second abort deadline and bounds streamed JSON to 64 KiB. Only an exact session/user match with backend status `active` returns true. A missing, mismatched or inactive session returns false; transport, malformed response, credential, redirect and provider-limit failures become sanitized `SessionVerificationUnavailable`. The API requires literal true on every write, including replay, or returns 401 before database acquisition; verification outages return 503. No credential or provider body is logged or returned. This check is not a substitute for JWT verification and is not distributed atomicity with a later database commit. References: Clerk [getSession](https://clerk.com/docs/reference/backend/sessions/get-session) and [Backend Session](https://clerk.com/docs/reference/backend/types/backend-session).
- `provisionApiAccount` and `updateApiAccount` in `api-account-writes.ts` use fixed operations `account.provision:v1` and `account.update:v1`, the verified subject and the parsed profile/patch. Both return 200 `ApiUser` plus `Idempotency-Replayed: true` or `false`; creation uses 200 because an already-existing profile is a valid unchanged result. Neither body nor response contains membership assignments. Authorization locks the current account inside the receipt transaction, including before replay. Retained deleted accounts are denied, and a missing account cannot receive an old unexpired provisioning response. PATCH never creates an account and updates only supplied fields.
- `runApiMutation` now takes a transaction-scoped advisory lock on the actor hash before receipt or account locks. This also serializes different keys for the same actor. `disableApiAccount` takes that same lock, records/preserves the first account tombstone (including for a subject with no prior local account) and purges all that actor's receipts atomically. It prevents delayed provisioning from reviving an account and prevents a racing write from leaving a cached profile after disable. It is an internal lifecycle primitive, not a public DELETE route or complete data-subject erasure: membership departure, retained profile removal, provider lifecycle verification and webhook wiring still need their own implementation.
- Expected mutation failures map to generic 400 `invalid`, 404 `not_found`, 409 `conflict`, 429 `rate_limited`, or 503 `unavailable`, without input details; unexpected failures remain 500. Request-local database cleanup and no-store responses apply equally to writes.

### Account linking by proof of the Telegram account (23 September 2026, no route yet)

A pilot invite proves possession of an invitation and is consumed by the Telegram consent flow; it is not proof that a Clerk session owns an already-linked Telegram member, and names, email, phone or member IDs never stand in for that proof. `packages/services/src/account-linking.ts` implements the separate challenge instead, in three internal steps backed by `account_link_challenges` (migration `0002_account_linking`). Nothing calls them yet: no HTTP route, no bot command, no deployment, and `POST /v1/me/link` stays 404 even with writes enabled.

- **`startAccountLink(deps, identity, key)`** runs through `runApiMutation` as `account.link.start:v1`. It locks the caller's live account, invalidates that owner's other challenges that are still open and unexpired, and inserts one bound to the hash of the calling session, valid for 15 minutes. It returns 201 with `{challenge_id, expires_at}` and no code. A completed or already expired challenge is left alone.
- **`issueAccountLinkCode(deps, challengeId, event)`** is the Telegram half and takes no session and no key. It accepts only a private `start` event on Telegram whose sender is the conversation, so the code can reach nobody but the owner of that account. Under the actor's advisory lock it locks the owner, the challenge, then the member, its family and its channel link, refusing a member who is not active or paused, one who has left, a deleted family and a blocked link. It binds the challenge to that family, member, channel link and the hash of the Telegram id, stores the hash of a fresh 22-character code, and returns the code for the bot to show. Reissuing for the same Telegram identity only rotates the code, spending no attempt and never extending the expiry; a different identity is refused, and a member already linked to another account is a conflict.
- **`completeAccountLink(deps, identity, key, challengeId, code)`** runs as `account.link.complete:v1`, scoped to the bound family and member. It requires the same session that started the challenge and the same account, re-locks the owner, the challenge and the target, checks the bound Telegram identity again, and compares the supplied code with the stored hash in constant time. A wrong code spends one of five attempts and answers `{linked: false}`; the fifth invalidates the challenge. On success it sets `members.user_id` when that member has none, marks the challenge completed, clears the code hash, writes an `account_linked` event, and answers `{linked: true, member_id, family_id}`. Repeating the call replays that answer through the receipt; a member claimed by another account, or a second member of the same family already held by this account, is a conflict.

The mechanism is therefore in place, but linking is still unavailable to a person: exposing it needs a route and a bot command, the consent copy that explains what linking does, and the same activation gates as the other writes.

Before production's account writes are enabled, apply the migrations there, configure its Clerk production instance and add its `API_IP_LIMIT` binding and its `ACCOUNT_WRITE_LIMITER` Durable Object binding, which on staging refused a burst of signed-in writes after the 20th on 26 September 2026 (staging's address binding did not act in its burst test of 25 September 2026, and the object replaced its write binding that day), wire verified disable/deletion lifecycle handling, review the notices/sub-processors, and run the provider smoke checks. The multi-connection PostgreSQL contention drill is done (§ "Durable mutation receipts" below).

### The lights of a family (23 September 2026)

`GET /v1/families/:familyId/lights` answers `MemberLight[]` for the caller's family: one row per kept-light member, read in that member's own local day. `loadApiLights` in `packages/services/src/api-lights.ts` takes the family authorization every other family read takes, then derives each state in this order: a paused member is `paused`, an unended away period covering her day is `away` with the day it ends, a day she has answered is `lit` with the time she answered, an unresolved quiet event on the day's exchange is `quiet` with its id, and anything else is `resting`. An answer counts for the local date it arrives on, whichever exchange it attaches to (flows §3.9): a message before the day's arrival attaches to the previous exchange, and a tap on an older arrival's buttons answers that older exchange, yet either answers her day. So `answered_at` is the earlier of the day's exchange's `answered_at` and her first `answers.received_at` on that local date (`dayAnsweredAt` over `firstAnswersByDate` in `repo.ts`, the rule the schedule and the quiet ladder read). Until 26 September 2026 the lights read only the day's own exchange, so after her tap on yesterday's arrival closed today's quiet and told the organisers "Everything is lit again", the app showed her resting (`api-lights.test.ts`, `answers.test.ts`). `usual_time` is her arrival time. After the kept-light members come those still **invited** — made by onboarding, not yet answered — with the state `none`: her light does not exist until she says yes, so she has no state of her own, but the organiser who has just set her up should not find an empty Today. Nothing is asked of her and nothing is scheduled; composing to her is refused until she says yes. A stranger, a family that is not the caller's and an unknown family all answer 404. The route is served wherever the API is (§ "Where the API runs").

### The Today screen (23 September 2026)

`GET /v1/families/:familyId/today` answers `ApiToday` for the caller’s family: `lights` exactly as the lights route answers them, `exchanges` with one entry per kept-light member who has an exchange in her own local day, and `tomorrow` with one entry per kept-light member whose next local day holds a turn, an ask, or a suggestion. `loadApiToday` in `packages/services/src/api-today.ts` takes the same family authorization and reads every day in the member’s own time zone, so a family spread across zones sees each person’s day and not the caller’s.

An exchange carries the asker’s name (null for Vela’s own hello, and for an ask whose asker was deleted), the ask, her latest answer with the time it arrived, the replies in the order they were written, and `seen_at` for the receipt chip. The exchange is the day's own, so it can wait for an answer while her light is lit: her tap today on yesterday's arrival lights her day (the lights above) and answers yesterday's ask, which the Exchanges list shows with her words. The app then reads her day from her light's `answered_at`, not from the exchange: under the ask it says she answered an earlier ask at that time, and "No word yet today" only while her day has no answer (`toToday` in `apps/app/src/data/useToday.ts`). Until 26 September 2026 it said "No word yet today" under any ask without an answer, beneath a light that read "answered 14:32". Her words are read as the read-back reads them: the transcript, else the text of what she wrote, else the choice she tapped, else the summary — so an answer that carried no words comes back with `text: null` and its kind, and the reader decides what to call it. A turn carries the holder (null until the evening prompt has chosen one, when nobody holds turns, or when the holder has left), `turn_pending` (true while no `turns` row exists for that day, so the app names nobody's turn before the prompt has chosen a holder), the ask already composed for that morning, and a suggestion — never both of the last two, because a morning holds one ask and offering a second would invite a 409. A `turns` row exists only once the evening prompt has run, so an entry is returned whenever there is a turn row, an ask **or** a suggestion; an ask composed before the prompt would otherwise leave the asker with nothing to show for it (spec A7: composing "returns to Today with the tomorrow card updated"), and the nightly job writes the suggestion days before the prompt. The suggestion is `{id, text, type, from_her_words}`, in the reader's own language, and is offered to every live member of the family except the kept-light member it is about (§ "Tomorrow's suggestion" below).

A stranger, a family that is not the caller’s and an unknown family all answer 404. The route is served by the pilot Worker under `/v1` wherever the API is on (§ "Where the API runs"), and on a developer’s own machine by `apps/worker/scripts/api-dev.ts` for the app to read (infra/README.md, section 9a).

### Composing an ask (23 September 2026)

`POST /v1/families/:familyId/exchanges` is the first write a family makes. It takes `ComposeAsk` — `recipient_id`, `type`, `text`, `when` (`tomorrow`, `date` or `whenever`), `date` for a `date` ask, `vote_options` for a vote, `on_behalf_of`, `suggestion_id` when the ask started from tomorrow's suggestion, and `media_ids` for a photo ask — and answers 201 with `ApiComposedAsk`. `composeApiAsk` in `packages/services/src/api-asks.ts` runs it through `runApiMutation` as `exchange.compose:v1`, scoped to the family and the recipient, so a repeat replays the first answer and writes no second ask.

Only the types an arrival can carry are accepted: `question`, `word`, `story`, `recipe` and `vote` from words alone, and, since 26 September 2026, `photo_choice` and `memory_photo` with the photos the app uploaded first (§ "Photos for an ask" below). Since 3 October 2026 a `voice_note` is accepted too: the asker's own recording is the ask (spec §4), so it needs a `voice_hello_id`, and without one it is 400. Its words default in the app to "Listen to my voice note." Her morning plays the recording first, then the words, with the heart and "I'm fine" to answer. `media_ids` names a photo ask's photos in the order she is shown them: two for a photo choice, one for an old photo and none for any other type, each named once, and never on a `whenever` ask; any other shape is 400. A photo that is not the family's, not the asker's to ask with, or deleted before the day after her morning is over answers 404 `not_found` with `details.reason` `photo_missing`, and nothing is composed. At delivery `mediaByIds` takes the recipient's family and cannot return another family's row, dropping an id the family does not own and logging it as `media_outside_family`.

Every date is the recipient's own local day. `tomorrow` is her next morning, a `date` ask must name a day after today and no more than 14 days ahead — retention clears an undelivered ask's words after 30 days, so nothing may be composed into that — and `whenever` carries no date at all. The one-ask-per-day rule is held by the recipient's member row, locked `for update` as the mutation's first statement, which is the lock `prepareDay` and the Telegram compose path take; `exchanges_one_per_day` stays the backstop whose firing is an incident, never a control path.

Two people in one family reaching for the same morning are different actors, so their actor advisory locks never meet and that row lock is the only thing between them — which the PGlite tests, on one connection, cannot prove. `packages/services/postgres-tests/api-compose-race.test.ts` puts both composes on her row through a third connection that holds it, then lets go: one gets 201, the other the 409 above naming the winner, and `exchanges_one_per_day` must not fire. A second race takes two different mornings, so the lock is shown to serialise without inventing a conflict. Both passed on PostgreSQL 18.6 on 24 September, in the whole drill's 36 tests. `pg_blocking_pids` names only a backend's direct blocker, so the second compose queues behind the first and not behind the holder; a race test that starts both at once leaves the queue order, and with it the winner, to chance.

A day already claimed answers **409** whose `details` are `{taken_by, date_alternative}`: who holds that morning (Vela when it is her own fallback hello) and the next one nobody holds within the window, or null. That is what A7 needs to say "Anna already has tomorrow morning" and offer the day after or whenever. The caller must be a live member of the family, and the recipient a kept-light member who is active and has not left; a stranger, another family, a paused recipient and an unknown family all answer 404.

**An ask started from a suggestion** (26 September 2026, ADR-31). `suggestion_id` names the suggestion the ask started from, even when its words were changed; a value that is not a uuid is 400. In the same transaction, after the exchange is inserted and so after the morning is known to be free, the mutation marks that suggestion used, but only if it is about the recipient, in this family, and not used yet: `used_at` is set and `ask_composed` carries `from_suggestion: true`. An id that matches nothing, one already used, another family's, or one about another member composes the ask all the same, marks nothing and records `from_suggestion: false`: the words are the asker's, a stale Today must never block a send, and a 404 would tell the caller whether someone else's id exists. A 409 marks nothing, because the refusal comes before the mark and the transaction rolls back. The first use keeps its time, and a replay returns the first answer without marking again. The field is optional, so the operation stays `exchange.compose:v1`. Once a suggestion is used, Today no longer offers it, and no second one is written for that day.

**The family group hears when tomorrow is taken** (24 September 2026). When the ask claims her next morning and the family has a linked Telegram group, the mutation writes one queued `system` row to that group — `group.ask_from_app`, "Mia asked Mom something for tomorrow morning." — with the asker as its member and the ask as its exchange, and returns it in `AfterCommit`; the route hands it to the queue once the transaction has committed, and `reconcile` sends it if that fails ("The quiet notice", After the commit). It never carries the ask's words, which are hers to hear first. A later morning or a whenever ask says nothing yet, and a replay says nothing again. The pilot Worker serves the route wherever the API's writes are on and hands the group's row to its outbound queue at once; `api-dev.ts` serves it only when a Clerk secret key is present, because a write needs the live session check that only Clerk's backend can make.

### Tomorrow's suggestion (26 September 2026)

Every kept-light member who can be asked has one suggested ask for each of her next mornings: what Today offers on the tomorrow card, and what "Use this" puts in Ask's field (build plan 3.3 and 3.4, ADR-31). It has no route of its own: Today reads it and composing uses it, so the planned `GET /families/:id/suggestions` and `POST /suggestions/:id/use` are dropped (§4).

**One row per member per local day.** Migration `0003_suggestion_days` gives `suggestions` a `local_day` (her own local date, as `turns.local_day`), a `bank_id` and a `lang`, the unique key `suggestions_one_per_day` on `(about_member_id, local_day)`, and CHECKs holding `type` to the exchange types and `lang` to the languages. `for_member_id` becomes nullable and the writer leaves it null: a suggestion is her morning's, not one holder's, because the holder is chosen only by the evening prompt and anyone in the family may compose. A row holds either a bank item, with `text` `''`, `lang` null, `prompt_version` `bank.v1` and `source` `{}`, so no family words at all; or an AI draft, whose `text` is kept in the language it was drafted in, with `prompt_version` `suggest.v1` and `source` `{ai_source}`. Both keep the bank item's id.

**The question bank.** `ASK_BANK` in `@vela/copy` (`packages/copy/src/ask-bank.ts`): 52 asks, 20 questions, 16 stories, 8 recipes and 8 words, the types an ask composes from words alone, each written to her in English and Traditional Chinese and each about her life, her knowledge or her opinions. `ask-bank.test.ts` holds every item to the catalogs' wording rules (`@vela/copy/rules`) and to `HEALTH_CHECK`, which refuses "are you OK", how she feels, her body, sleep, medicine, doctors, loneliness and worry, in both languages; ids are only ever appended. The Traditional Chinese awaits a native reader, who also decides whether an ask addresses a parent as 您 or as 你.

**The writer.** `writeSuggestions` in `packages/services/src/suggestions.ts` runs in the pilot Worker's nightly cron (03:20 UTC), after `rollupMetrics` and `applyRetention`, and only where `API_V1` is `on`: development and staging. Production's API is off and its database has none of 0001–0003, so production writes no suggestion and never asks the model for one. Retention and the writer each run whatever the other did; a failure is logged as `nightly_job_failed` with the job's name, and the run then fails as `cron_failed`. Each run writes her local days one, two and three ahead, so tomorrow's suggestion exists long before its morning in every zone, and a missed night still leaves tomorrow written. It writes for every member compose could ask (`canBeAsked` in `askable.ts`, the predicate compose uses: active, light on, consented, not left) in a family that has not ended. A day that already has a suggestion is left as it is, and a day an ask not withdrawn already holds gets none. The run returns `{written, existing, claimed, inactive, failed}` and logs it as `suggestions_written`; a member-day that throws is logged as `suggestion_failed`, and the others are still written.

**The pick** (`pickBankItem`) is a pure function of what is stored, so a second run, or a racing writer, picks the same item. The weekday proposes a type, Sunday first: question, story, question, recipe, story, question, word. A story, a recipe or a word already asked for either of the two days before moves it on to the next type in that order, and so does a story on the family's story day; a question never does, since any type can be composed as one. Never picked: an item suggested to her within 42 days, or one of its near-duplicates (items that share a `group`); an item an ask was composed from, at any age; and an item suggested to another member of the family within a week. An item whose topic she was given within two days of the day is passed over while the day's type has another. Among what remains, an item with no near-duplicate comes first, and one is taken by a hash of her id and the day; when nothing remains, the item least recently suggested to her, one an ask was composed from last.

**The model's draft.** The writer then calls `ai.suggest` (`suggest.v1`) with the family's first active organiser's language (English or Traditional Chinese) and name, her display name, the bank item's type, the people, places and plans in her answers of the last 14 days (never health words or dates; at most 20, each at most 120 characters), no family dates, and her latest ask from a person in the last 30 days. The draft is stored only when the call succeeded with a bank type and words that pass `HEALTH_CHECK` in both languages, `SURVEILLANCE_WORDS`, `GENDERED_PRONOUNS` and `FORBIDDEN_ZH_TW`; otherwise the bank item is. Every call the model answered is logged in `ai_calls` in the write's transaction, with `input_ref` `{member_id, for_date, bank_id}`, even when another writer or an ask took the day meanwhile; a failed call also logs the warning `suggestion_ai_failed`. With AI off, as development and staging are configured, no call is made: the bank item is stored, and no `ai_calls` row or warning is written. So no deployed environment asks the model for a suggestion yet.

**Today's read.** For each kept-light member, the row for her next local day that is not used, rendered in the reader's `members.language`, or English when the bank has no text in it: the draft when it was written in that language and retention has not cleared it, and otherwise the bank item it stands on, with that item's type. Two organisers who read different languages each see it in their own. `from_her_words` is true only for a draft built on something she mentioned. It is offered only for a morning an ask could take: never beside a composed ask, never about a member who cannot be asked or in a family that has ended, and never to the kept-light member about herself (spec §7).

**Retention.** `applyRetention` clears `text` 30 days after the row was written, as before. `bank_id`, `type` and `local_day` hold no family words and stay, so a cleared draft reads as its bank item, and the 42-day rule and the rule for used items outlive it.

**Locks.** The writer picks and calls the model outside any transaction, then in one takes her family `for key share` and her member row `for no key update`, which a compose's `for update` excludes; checks again under the lock that she can still be asked, that the family has not ended and that no ask holds the day; and inserts with `on conflict do nothing` on `suggestions_one_per_day`. So a writer and a compose reaching for her morning queue on her member row, and two writers on one day leave one row without the unique key firing (code design §8, "Lock order"). `postgres-tests/suggestions-race.test.ts` holds three races, each queued on her row behind a connection that holds it: two asks for different mornings started from one suggestion mark it once, at the first ask's time, with `from_suggestion` true for that ask alone; two writers reaching one day write one row, return `written` and `existing`, and log both model calls; and a compose ahead of a writer on the same morning leaves the ask and no suggestion, and Today shows the ask. CI's `contention-drill` job runs them on every push with the rest of the drill. On 26 September 2026 all three passed there, and with each guard broken on a throwaway branch each failed as expected: the used time moved to the second ask's, the second writer hit 23505, and the writer wrote over a claimed morning.

**Before staging runs it.** Staging's database needs `0003_suggestion_days` before this code is deployed there, applied by the founder as 0001 and 0002 were (infra/README.md §9a, step 9.2). The migration starts by deleting every `suggestions` row: nothing but the local dev seed ever wrote one, and that seed refuses any database that is not local, so staging and production have none, while a laptop seeded earlier has one with no day and no bank item. The dev seed now writes its suggestions through `writeSuggestions`, with AI off. On staging the first suggestions come with the first nightly run after the deploy, at 03:20 UTC (11:20 in Taipei).

### Photos for an ask (26 September 2026)

A photo choice shows her two photos and asks which one she likes more; an old photo shows her one and asks for its story (build plan 3.4, ADR-33). The app uploads each photo first, as a JPEG, and the ask then names the ids it got back (`media_ids`, § "Composing an ask" above). Two routes carry the photos: `POST /v1/families/:familyId/media` keeps one, and `GET /v1/families/:familyId/media/:mediaId` shows one to the family. Not yet deployed.

**The upload.** The body is the photo's own bytes, not JSON: a photo in base64 would not pass the JSON routes' 4 KiB, and a raw body costs no parser. The request carries `Content-Type: image/jpeg` (parameters allowed, any case), no `Content-Encoding` but `identity`, an `Idempotency-Key` and the bearer token, and answers 201 with `ApiUploadedMedia`: `{id, kind: "image", width, height, bytes, expires_at}`, the size being the photo as Vela keeps it, with `Idempotency-Replayed`. `uploadApiMedia` in `packages/services/src/api-media.ts` runs it through `runApiMutation` as `media.upload:v1`, scoped to the family. Its input is the cleaned photo's SHA-256, byte count, width and height, never the bytes: the same key with the same photo answers the first upload's row again, even when the phone's bytes differ only in what cleaning drops, and the same key with another photo is 409. Any live member of the family may upload, as any member may compose, so no role is asked for and the route never answers 403. It is a write: it needs the write capability, and without it answers 404 as every write does.

**Body limits: ADR-29 refined for this one route.** The JSON routes read at most 4,096 bytes within 10 seconds, and they still do. This route reads at most 1 MiB (`MAX_UPLOAD_BYTES`, 1,048,576 bytes) within 60 seconds (`MAX_UPLOAD_READ_MS`): the phone sends a photo re-encoded at 1600 pixels on its long side and quality 0.8, well under the cap, and a phone on a slow network needs the time, which costs no CPU while the Worker waits. A declared `Content-Length` over the cap is refused from the headers, and the bytes are counted as they arrive whatever was declared. So are the pieces they arrive in: at most 16,384 reads (`MAX_UPLOAD_READS`, 1 MiB in pieces of 64 bytes on average, where a phone sends a kilobyte or more at a time), since each read costs memory and CPU of its own, and a body trickled in more is 400. The 60 seconds are one timer that cancels the read, never a promise raced against every read. Every cheap refusal comes before the body is read, in this order: authentication (401); whether this API keeps photos at all (503); the headers (400 without a valid key, 415 for another type or encoding, 413 for a declared length over the cap); the account's write limit and the live session check (429, 401, 503; § "Where the API runs"); the family (404); only then the body (413, 408, 400); and then the service, which cleans the photo and writes its row.

|---|---|---|---|
| 201 | — | — | Kept. `Idempotency-Replayed: false`, or `true` for the same key and photo again |
| 400 | `invalid` | — | No valid `Idempotency-Key`; an empty body; a body sent in more than 16,384 pieces; a body stream that fails |
| 400 | `invalid` | `malformed` | A JPEG that cannot be walked to its end: truncated, no EOI, a scan before its frame, a segment longer than the file, a restart interval of other than 2 bytes; or one whose walk would take more than 1,024 markers or 65,536 escapes |
| 400 | `invalid` | `dimensions` | A side of 0, a long side over 4,096 pixels, or one side over 20 times the other (within Telegram's limits for a photo) |
| 401 | `unauthenticated` | — | No token or a bad one, or a session Clerk no longer holds active |
| 404 | `not_found` | — | Not a live member of the family, an unknown family, or a family that has ended |

**Cleaning.** The phone re-encodes every photo as a JPEG before it sends it (`expo-image-manipulator`), which turns HEIC, PNG and WebP into JPEG and drops most of what a camera writes into a file; nothing promises that, so the Worker enforces it. `cleanJpeg` in `packages/services/src/media-jpeg.ts` makes one linear walk over the file's markers, decodes nothing and re-encodes nothing, and keeps exactly: SOI; a JFIF APP0 when the photo has one, rebuilt as the standard 16 bytes with the original's version and density and no thumbnail, since the original's thumbnail can show the photo before it was cropped; the Exif Orientation alone, as a minimal APP1 holding a TIFF header and an IFD0 with that one entry, written only when the original says 2 to 8 (read in either byte order), so a portrait photo a phone stored sideways still arrives upright; an APP2 ICC profile (its colours; its description can name the device, which ADR-33 accepts); the first APP14 Adobe segment, rebuilt as its standard 12 bytes so that nothing written after them comes along; the DQT and DHT tables and the DRI restart interval, which must be exactly its 2 bytes; one SOF0, SOF1 or SOF2 frame, whose width and height are read; each SOS with its entropy-coded data byte for byte, so a progressive file's scans all survive; and EOI. Everything else is dropped: the rest of the Exif (GPS, the time, the camera, maker notes and the Exif thumbnail), XMP, MPF, Photoshop and IPTC, every other APPn, COM, DAC, DNL, DHP, EXP and JPGn, and every byte after EOI, where a Samsung or MPF trailer holds a second image with its own Exif. The walk's work is bounded as well as its input: a phone's photo has fewer than 100 markers and about one escape (a stuffed FF00, a restart marker or a fill FF) in 256 bytes, so a file with more than 1,024 markers (`MAX_JPEG_SEGMENTS`) or 65,536 escapes (`MAX_JPEG_ESCAPES`) is refused as `malformed`, which keeps the costliest file it accepts to about 3 ms of CPU; a crafted megabyte of tiny segments or FF-dense scan data took 16 to 40 ms without the bounds.

**Where it is kept, and the object before the row.** The service stores the cleaned photo under a key minted for this one attempt, `asks/<familyId>/<random token>.jpg`, and only then writes its `media` row in the receipt's transaction: the family; `uploaded_by`, the caller's member as the in-transaction authorization found it; `kind` `image`; the storage key; no channel and no provider ids; `mime` `image/jpeg`; its bytes, width and height; `kept` false; and `expires_at` 30 days on (`MEDIA_RETENTION_DAYS`). Retention deletes it as it deletes any media row: the object, a proof, and its id from every exchange's options and `media_ids`, except a photo choice's `media_ids`, which keeps the id in its place, naming nothing, so her pick still reads by its place (flows §3.15). A photo the cleaning refuses is refused before anything is stored. Nothing but the row can ever name the key, so a refusal the service or the receipt helper decided inside the transaction (404, 409, `photo_limit`), and a replay, delete the attempt's own object at once. After any other failure, whether the commit happened is unknown: the row is looked for first, outside the failed transaction, and the object is deleted only when the row is seen to be absent; otherwise it is kept and `media_upload_commit_unknown` is logged. A delete that fails logs `media_orphan_delete_failed`. Both lines carry the family id and an error label, never the key. So an object no row names is left by an isolate that dies between the put and the commit, by a delete that fails, and by a failure after which the row cannot be looked for. The backstop is a lifecycle rule that deletes objects under `asks/` 32 days after they were written: a setting of the bucket itself, not of `wrangler.jsonc`, and not set yet. It is added to `vela-media-staging` with `wrangler r2 bucket lifecycle add` when this change reaches staging, and production's bucket needs the same rule before its API is turned on (data map, row 11 and gap 21). Because of that rule, a family book that keeps photos (spec A8) must copy them out of `asks/`.

**Volume limits.** Inside the transaction, where no concurrent upload can slip past them: an account keeps at most 20 photos from the app in any 24 hours, across all its families (`MAX_PHOTOS_PER_ACCOUNT_DAY`), and a family holds at most 60 photos from the app that are neither kept nor past their deletion date, whoever uploaded them (`MAX_LIVE_PHOTOS_PER_FAMILY`). Photos from Telegram are not counted. Over either, the upload answers 429 `rate_limited` with `details.reason` `photo_limit`, and a replay of an upload made before the limit was reached still answers. An account's own uploads are ordered by its actor lock, and a family's members, who are different actors, by a transaction-scoped advisory lock on the family, taken after the actor lock and before any row lock and by nothing else, so it closes no cycle. These are the real caps: the Workers Rate Limiting bindings do not act on workers.dev (§ "Where the API runs"), and the per-account write limit still counts each upload as a write.

**Who may see a photo.** `GET /v1/families/:familyId/media/:mediaId` answers the photo's bytes, 200 with `Content-Type: image/jpeg`, `X-Content-Type-Options: nosniff`, `Content-Disposition: inline` and `Cache-Control: no-store`. The Worker reads the object and passes it on: there is no signed URL, which the Worker's R2 binding cannot make and for which it holds no S3 keys, no public bucket and no `r2.dev` address. `readApiMedia` serves an image of that family, stored and a JPEG, to a live member of it who uploaded it, or when the family already shares it: named by one of the family's exchanges (a photo ask), or carried by an answer or a reply in one. An upload nobody has asked with yet is therefore its uploader's alone. Everything else answers 404 alike: an id that is not a uuid, before the database is opened; a stranger and an unknown family; another family's photo asked for through this family's path; an unknown id; a voice note; a photo only Telegram holds, which has no storage key (the app shows a placeholder, since fetching it from Telegram would need the bot token, which the API does not hold: it never builds the pilot's deps, ADR-29); an object no longer in the store; and any photo while this API keeps none. The route is a read, served without the write capability; a store that fails answers 500.

**Family scope, at every step.** The upload's family comes from the path and is checked again inside the transaction; composing takes only the family's own photos that the asker uploaded or the family shares, `for share`, as above; the arrival reads them through `mediaByIds`, which takes the family; and the read puts the family in its query.

**Composing with photos.** After her member row is locked and before her morning's exchange is (code design §8, "Lock order"), the photos an ask names are taken `for share`, and each must be the family's, an image, the asker's to ask with as the read route decides, and kept or not deleted before the end of the day after her morning in her own time zone, when a pick is still resolved against it. Otherwise the ask answers 404 `photo_missing`, "That photo is no longer here.", and the app asks for it to be chosen again. The share lock is what keeps retention off the photos until the ask commits: retention takes a photo's row `for update` before it removes its id from every exchange, so either it waits for the ask and then removes the id from it too (from an old photo; a photo choice keeps it in its place, naming nothing, flows §3.15), or the ask waits for retention and finds the row gone. The ids enter the receipt's fingerprint, the operation stays `exchange.compose:v1`, and `ask_composed` counts the photos (`media`).

**Delivered as uploads.** At the arrival, a photo Telegram holds goes by its file id, and a photo Vela keeps by its storage key, once `head` shows its object is still there (`mediaRefOf` in `arrivals.ts`). One whose object is gone, or any while storage is off, is left out and logged as `media_not_sendable` with a count, and on a channel whose adapter does not upload bytes (`uploadsStoredMedia` in `outbound-media.ts`: every channel but Telegram) every stored photo is left out the same way and logged as `media_not_sendable_on_channel` with the channel, so a photo choice short of two goes as a question with the photo it has, before its text and buttons are drawn; a store that cannot say throws, and her morning is tried again. Since 28 September 2026 the arrival also checks what compose checked, against the morning it is actually sent on: a photo neither kept nor without a deletion date whose `expires_at` falls at or before the end of the day after that morning, in her zone, is left out as a gone one is and logged as `ask_media_expiring` with a count, so an ask carried to a later morning, or a group photo that waited, never shows her a 1 and 2 over a photo retention deletes before she taps (flows §3.7). An ask without words that has no photo left says so, `arrival.photo_gone`, rather than "Mia asks:" over nothing. Within the message's ten files the ask's photos come first and the read-back's voice notes take what is left, so a photo choice's pair is never cut. The outbound row's payload holds the storage key, never a URL, so no link to a family's photo is made or kept for Telegram. LINE takes media only by URL, and its adapter's `mediaUrl` is not wired, so no stored photo reaches LINE yet (ADR-33, Consequences). On every attempt the gateway loads the bytes (`loadOutboundFiles` in `outbound-media.ts`) and hands them to `ChannelAdapter.send(message, files)` (§12). The Telegram adapter uploads them as multipart/form-data: `sendPhoto` with the file for one photo, and for an album `sendMediaGroup`, naming each upload `attach://p<index>` beside any file ids, in her order; a message whose photos Telegram holds still goes as JSON. An object missing at the send, or a store that cannot read it, is `ChannelSendError("unavailable")` and is retried as any passing failure is, at 5, 15 and 30 minutes and then failed (flows §3.7), never sent with 1 and 2 under one photo. Telegram's own `file_id` for the upload is not written back, so the repeat uploads the photos again, at most 2 MiB for a pair.

**Her words translated (3 October 2026).** Her answer on Today and in the list also carries `translation`: `{lang, text}`, her words in the family's language as the pipeline translated them for the group (flows §3.10), or null where her language is the family's or no translation is done. `text` stays her own words. The app shows the translation to a reader whose language it is, and offers her words through the Exchanges language switch.

**What the app reads.** Every exchange on Today and in the list carries `photos`, `{id, width, height, stored}` for each of the ask's images in the order she was shown them; `stored` says whether the read route can serve it, and a photo retention has deleted is no longer listed, with no empty slot in its place, so a photo choice that lost one photo lists one. Her answer carries `picked_media_id`, the photo her latest pick chose on a photo choice, kept when she went on to say something, and null otherwise, and since 28 September 2026 `picked_number`, 1 or 2 as her buttons numbered it, set whenever `picked_media_id` is: once that photo is deleted it is no longer in `photos`, and the number is how the app still says which one she picked ("picked photo 1" for a pick with no words of its own). It is never a place in `photos`. A pick is read by its place in `media_ids`, which retention keeps for a photo choice, so a tap after a photo was deleted is still recorded as the photo she was shown there, and still lights her day (flows §3.9). `GET /v1/me` carries `photos`: whether this API keeps photos, so the app can switch its photo asks off before anyone picks one; the upload's 503 stays as the backstop.

**Where it works.** Staging's `MEDIA_STORAGE` is `r2`, with the bucket `vela-media-staging`, since 26 September 2026 (infra/README.md, section 1, step 3), so once this change is deployed there its uploads are kept in that bucket. The pilot Worker in development runs with `off`: its upload answers 503 `media_storage_off`, its read 404, and `GET /v1/me` says `photos: false`. `apps/worker/scripts/api-dev.ts` keeps photos in its own process's memory, lost when it stops, and nothing on disk, and serves the upload, like every write, only with a Clerk secret key; the app's web preview can show photos only against it, because staging refuses any request carrying `Origin`. Production's API is off (§ "Where the API runs"). A store that cannot be built leaves photos off and the rest of `/v1` answering, since a photo setting is no reason to close the whole API (ADR-29's isolation).

**Tests.** `media-jpeg.test.ts` walks files built byte by byte in the test (every segment kept or dropped, Orientation 6 in both byte orders, trailers, progressive scans, each refusal); `api-media.test.ts` in the services covers the row, replays, conflicts, orphans, both limits, retention and who may read; the Worker's `api-media.test.ts` covers the order of refusals, each status above, the body's cap and deadline, and the read's headers; `photo-asks.test.ts` covers composing, delivery (a photo deleted before the day after the morning it is sent on left out), what Today shows, and her pick after a photo's deletion; and `telegram/upload.test.ts` the multipart calls. The contention drill (`postgres-tests/`) adds `api-media-upload-race.test.ts` (the same upload twice, one key for two photos, and an account's and a family's last place at the limit) and `api-compose-photo-race.test.ts` (an ask composed while retention deletes its photo, in both orders).

### The Exchanges list (24 September 2026)

`GET /v1/families/:familyId/exchanges` answers `ApiExchangePage`: the same card Today shows, with the day it was for and the moment it arrived, newest first. `loadApiExchanges` in `packages/services/src/api-exchanges.ts` takes the same family authorization the other family reads take, and puts the family in the query itself: membership is not permission to read a nested id.

Only days that happened. An ask still waiting for its morning belongs on Today's tomorrow card, and a withdrawn one belongs nowhere, so the list carries only exchanges that were delivered. It reaches back `EXCHANGE_LIST_DAYS` (30) days and then stops, which is where the family book takes over (spec A8) — and is also where retention clears an exchange's words, so a longer list would be a list of blanks. That floor is applied to **every** page, not only the first, so a cursor invented by a caller cannot walk past the end the route promises.

Paging is on `exchanges.id`, which is uuidv7 and so already in the order the list reads. `scheduled_for` cannot carry a cursor: it is nullable, its index is `desc nulls first`, and two exchanges in one family can share a day, so it has no total order. A cursor that is not a uuid is ignored rather than trusted. `next_cursor` is null at the end.

The route is a read, so it needs no write capability and is served whether or not a Clerk secret key is present — unlike composing, which needs the live session check.

### Replying (24 September 2026)

`POST /v1/exchanges/:exchangeId/replies` takes `ComposeReply` — `{text}`, one to 1,000 characters of valid text — and answers 201 with `ApiReply`. `replyToApiExchange` in `packages/services/src/api-replies.ts` runs it through `runApiMutation` as `exchange.reply:v1`, with the exchange id in the fingerprint, so one key cannot be spent on two exchanges.

**Words only.** A heart, a laugh or a hug is the same `replies` row a Telegram reaction writes, and the Telegram path makes a member's reactions *equal* to their platform set on the message reacted on — deleting any of that member's reaction rows it does not see that no other message of the exchange carries (`reacted_message_ids`, which an app reaction would leave empty), whatever their channel — while `replies_one_reaction_idx` has no channel column. An app reaction would vanish the next time that member reacted in the group, or collide with the reaction they already made there.

**Authorization comes from the exchange.** The path names no family, so no family middleware runs: the service locks the exchange `for update` in `authorize` — which `runApiMutation` runs on every attempt, a replay included — reads its family, and checks the caller is a live member of it. An exchange that does not exist, belongs to another family, was withdrawn, never reached her, or is older than the Exchanges list's thirty days all answer 404 alike, and so does a family that has ended. The same row lock serialises two members replying at once, which the actor lock does not, and the state is re-read under it before the transition, so a reply after the read-back leaves `read_back` where it is and `replied_at` keeps the first reply's time. `postgres-tests/api-reply-race.test.ts` proves it: two members' replies queued on the exchange row, a minute apart on their own clocks, leave both replies and the earlier time. The clocks are the point — `replied` plus a reply is `replied` again, so the state cannot show a lost update, and on one shared clock an overwrite writes the same instant it replaces; with `?? now` removed, the test sees the later time.

**Two refusals** carry `details.reason`: `not_answered` (409) when she has not answered yet, so there is nothing to reply to; and `her_own` (403) when the caller is the kept-light member herself — she may hold an account, and her own reply would be read back to her by name the next morning. The Telegram path keeps an early reply and logs a warning; this service has no logger, so it refuses instead.

**Which replies she hears.** Her next arrival reads back only her latest delivered exchange (`loadReadBack`), so a reply to any older one is kept for the family and never heard. Every card on Today and in the list carries `replies_reach_her`, and every reply `reaches_her`, computed by `readBackExchangeId` in `repo.ts` with the same selection; the app words the composer from it rather than promising a read-back it cannot keep. One window remains: the arrival captures its reply ids when it is enqueued and stamps them when it is sent, so a reply written in the seconds between the two is neither read back nor, the day after, still on her latest exchange.

The mutation sends nothing and wakes nothing — a reply reaches her through the next arrival, which reads the database. It needs the write capability, like composing.

### Creating a family (24 September 2026)

`POST /v1/families` takes `CreateFamily` — a two-letter `country` and `kept_light_member`: `display_name`, `address_form`, `language`, `tz`, `wake_time` — and answers 201 with `ApiCreatedFamily`: the family, the organiser's member id, her invited member with the arrival time half an hour after she wakes, and her invite: the link, when it expires, and `invite.text`, the words the organiser sends her, in her language (spec A4, copy key `invite.for_her`). `createApiFamily` in `packages/services/src/api-families.ts` runs as `family.create:v1`.

**The same rows Telegram onboarding writes**, through the same helpers (`insertInvitedMember`, `insertInvite`, `regionForCountry`): the family, the caller as organiser (`primary_surface` `app`, linked to the account), and her as an **invited** kept-light member — light off, not consented, out of the turn rotation — with a single-use invite good for a week. Nothing about her is consented here. The link opens the bot, which reads her `consent.request` and records her answer exactly as it does for a family made in Telegram; a test runs that flow against an app-made family, and until she says yes nobody may ask her anything.

The caller's account must exist first (`POST /v1/me/provision`), because the organiser's name, language and time zone come from it; a caller without one gets 404. An account that already runs a family gets **409** with `details.reason` `already_organiser`: the app shows one family, and a second would sit behind it with nothing to reach it by until there is a family switcher. That check is made in `mutate`, not `authorize`: `authorize` runs again on a replay, when the caller already *is* this family's organiser, and would refuse the replay its own answer. **No constraint backs it**: `members_family_id_user_id_key` keeps one account out of one family twice, not out of two families, so the rule is exactly as good as that check and the actor lock that runs one create at a time. `postgres-tests/api-family-create-race.test.ts` queues two creates from one account, with two keys, on that lock: one family, and a refusal that leaves no family, member, invite or event behind. With the check removed, the same test makes two families.

A1's age, city and "lives alone" are not asked: nothing stores or uses them, and the privacy notice does not cover them. The response carries the invite token, so the receipt that replays it holds the token for its 24 hours; it is never logged. The route needs the write capability and a family capability of its own — a token source and the bot the link opens — and answers 404 without them.

### The family (24 September 2026)

`GET /v1/families/:familyId` answers `ApiFamily`, what You shows (spec A12): the family's name and plan; `me`, the caller's member id and role; every live member — invited, active or paused, never one who has left — in the order they joined, each with a `light` of `on`, `waiting` (invited and not yet answered, which is how onboarding leaves a kept-light member, and how the lights row reads her) or `off`, and, where a subscription covers them, its status, trial end and period end; and `nearby`, the people who could look in, each with the member they are near and `consent` `yes`, `no` or `waiting`. `loadApiFamily` in `packages/services/src/api-family.ts` takes the same family authorization as the other family reads.

**The people nearby are for the organisers**, who set them up; anyone else gets `nearby: null`. **No number is in it**, for anyone: a number is given only in the quiet notice, to the people the notice is for. A contact near a member who has left is not listed. Prices are not in it either — the plan card is A13's, and nothing charges yet. A stranger, a family that is not the caller's and an unknown family all answer 404. Since 27 September 2026 an organiser also reads `told_if_quiet`, how they would be told if her morning went quiet, and anyone else reads null (§ "Push").

### Starting the trial (24 September 2026)

`POST /v1/families/:familyId/plan/trial` takes `StartTrial` — `{member_id}`, the kept-light member it covers — and answers 200 with `ApiTrial`: her member id, the subscription's status and when the trial ends. `startApiTrial` in `packages/services/src/api-trial.ts` runs it as `plan.trial:v1`, for the family's **organisers only**, since the one who pays is an organiser.

Her member row is locked first, the lock her arrivals and asks take, so two organisers starting at once make one trial. With no subscription yet, it writes one: provider `trial`, status `trial`, `trial_ends_at` thirty days on (`TRIAL_DAYS`), the caller's account as payer, no price and no interval; and records `trial_started`. Two refusals, 409 with `details.reason`: `not_answered_yet` before her first answer (spec §16: the trial is "30 days after her first answer") and `light_off` when her light is not on. A member of another family, or one who has left, answers 404; her membership is checked in `authorize`, before the mutation helper's own scope check, whose refusal is not a 404.

**Nothing is charged or gated.** The pilot is free (spec Appendix A), no service checks the plan, and `families.plan` is left as it is: nothing would turn it back when the trial ends, because nothing ends a trial yet. The subscription row carries it, and `GET /v1/families/:id` shows it on You. Lapse, grace and checkout wait for billing.

### Pausing and leaving (24 September 2026)

`POST /v1/families/:familyId/members/:memberId/pause` takes `PauseMember` — `{paused}` — and answers 200 with `ApiMemberPause`, the member's status after it. `POST /v1/families/:familyId/members/:memberId/left` takes an empty body (`LeaveFamily`) and answers 200 with `ApiLeft`, the member and when they left. `pauseApiMember` and `leaveApiFamily` in `packages/services/src/api-members.ts` run them as `member.pause:v1` and `member.leave:v1`. An organiser's Leave that leaves the family with no organiser who can be told of a quiet morning (the other active organiser has no unblocked Telegram link and, while push is on, no phone that can be told) writes the founder's `admin.organisers_unreachable` in its transaction and hands it to the queue after the commit, on the first attempt only (ADR-34).

**Only one's own membership.** A member id that is not the caller's answers 404, as an unknown one does. Pausing an organiser's parent is not this route: she pauses in her own chat, and a family's absence is away mode (§5).

**What they do.** A paused member holds no turns — the rotation takes active members only — and a paused organiser is not sent the quiet notice, which goes to active organisers. Resuming makes them active again. Leaving sets `left`, `left_at` and `turns_in` false, as the founder's `mark_left` does, records `member_left` with `source: "app"`, and retention deletes the membership thirty days on. Asking for the state one is already in answers it as it stands. Pausing records no event: the events table's check names no pause, and adding one is a migration.

**Two refusals**, both 409 with `details.reason`: `last_organiser` when the caller organises the family and no other organiser is active — someone must still be told when her light goes quiet, so neither a pause nor a leave may take the last one away, and a paused organiser does not count; and `kept_light` when the caller keeps a light, whose pause and stop go through her own chat, where her arrivals, her health-words yes and her schedule are handled together (flows §3.13). The family's organiser rows are locked in id order before the caller's own, so two organisers pausing at once queue, and the second sees that the first is paused.

**Leave authorizes itself.** Once the caller has left they are no longer a live member, so the family check would refuse the replay of the very leave that made them one. The route has no family middleware; `authorize` accepts the caller's own row in a family that still exists whether it is live or left, and a later leave answers the time they left. The app clears everything it has read when a leave succeeds, and `/v1/me` then lists no family, so Today sends the reader to onboarding.

### The quiet notice (24 September 2026)

`GET /v1/quiet/:quietEventId` answers `ApiQuietNotice`: whose light it is, when today's ask reached her and when it was asked again, her usual answering time once there are enough answers to know it, when she last answered, when the event opened, `wait_until`, `resolved` (the outcome, when, and who said she was fine), and the people nearby who have said yes, with their numbers. Facts only — never her words. `loadApiQuiet` in `packages/services/src/api-quiet.ts` reads the family from the event, since the path names none, and answers **the family's organisers only**, as the Telegram notice goes only to them: the numbers are given to the people the notice is for. Anyone else, an event that does not exist and an id that is not a uuid all answer 404 alike.

`POST /v1/quiet/:quietEventId/fine` and `/wait` take an empty body (`QuietAction`) and answer 200 with `ApiQuietState` — the notice without its contacts. `resolveApiQuiet` runs them as `quiet.fine:v1` and `quiet.wait:v1` through the functions the Telegram buttons use (`resolveQuietAsFine`, `waitOnQuiet` in `quiet.ts`), so the two surfaces cannot close or delay an event differently. The event is locked `for update` in `authorize`, so a 404 is decided on every attempt including a replay. An event already settled — she answered a moment before the tap, or another organiser said she is fine — is answered as it stands rather than refused: the tap has nothing left to do, and the sheet shows how it was settled. The answer leaves out the contacts because it is kept a day to replay, and a number must not outlive the yes that let the family have it.

**A deadlock with her answer, found and fixed (24 September 2026).** Her answer and the quiet detector lock the exchange and then its quiet event; "she's fine" — here and on the Telegram button — locks the event and then writes the others' messages as outbound rows whose foreign key is that exchange, and each such insert takes `for key share` on it. While the exchange was locked `for update`, that closed a cycle, and PostgreSQL broke it by aborting one side: in the contention drill, **her answer** when it met a tap, and the detector when it did. Her answer was not lost — `handleInbound` rethrows, the webhook answers 500 and Telegram delivers the update again — but it was late by Telegram's retry, with an `inbound_failed` error on the one path that must never look broken, and a tap that lost to the detector answered the organiser 500. Both exchange locks are now `for no key update`, which still excludes every other writer of the row and admits only foreign-key checks; nothing on those paths deletes an exchange or changes its id. `postgres-tests/quiet-notice-race.test.ts` holds both races, fails on the old lock with SQLSTATE 40P01, and also covers her answer winning (the tap shows `answered_late` and sends nothing) and two organisers tapping at once (one close, one message to the other).

**After the commit.** "She's fine" tells everyone else who was told, and "wait" moves her scheduler's alarm; a mutation may not send a queue job or reach the scheduler, because both would outlive a rollback. So the mutation writes the messages as `queued` outbound rows (`insertOutbound`, the row half of `enqueueOutbound`) and marks her wake due, and returns an `AfterCommit` — the row ids and the members to wake — which the route hands to `runAfterCommit` once the transaction has committed. A replay returns nothing to do. If the handover fails, or the runtime has no `nudges` (the local `api:dev` server has none), nothing is lost: `reconcile` re-drives an outbound row still queued after ten minutes and ticks a member whose wake is overdue. The failure is logged as `api_after_commit_deliver_failed` or `api_after_commit_wake_failed` and the route still answers 200, since the write stands.

A quiet event opened during the learning period notifies nobody for its first eight hours, but it is a row like any other, so the light reads `quiet` and the app's organisers see the sheet at once: that is the in-app-only quiet the spec asks for. **Built 2 October 2026:** `ask-to-check` (§ "People nearby", On Telegram). **Built 2 October 2026:** `POST /v1/quiet/:quietEventId/useful` with `{useful: boolean}`, through `runApiMutation` under the event's row lock, by any organiser of her family once the morning is settled (409 `not_settled` before), a later tap replacing the verdict; it answers `ApiQuietState`, and the notice and state carry `useful` (null until someone answers). The app's sheet asks "Was this notice useful?" once the morning is settled.

### Push (27 September 2026, ADR-34)

Built, and switched off in every environment: the pilot Worker's `PUSH_SEND` is `off` in development, staging and production, and `src/wrangler-config.test.ts` pins all three, so no push is made or sent and nothing reaches Expo, Apple or Google, while the routes below record phones, ready for the switch (build plan 3.8). Staging's turn waits for the founder's Expo, Firebase and, for iPhones, Apple steps and the Worker's access token (`infra/README.md`, section 9); any real family's waits for a privacy notice version that names Expo, Apple and Google (the production gate, § "Authentication and family-access foundation" above).

**Registering a phone.** `POST /v1/me/devices` takes `RegisterPushDevice` — `{installation_id, token, platform, permission, quiet_channel_blocked}`: a uuid the app makes once per installation and keeps; the Expo push token (`ExpoPushToken`: `ExponentPushToken[…]` or `ExpoPushToken[…]`); `ios` or `android`; what the phone allows, `granted`, `denied` or `provisional`, which the app reads from iOS's own status on an iPhone; and whether Android's `quiet` notification channel is blocked in the phone's settings — and answers 200 with `ApiPushDevice`, the same without the token and with `registered_at`. `registerApiPushDevice` in `packages/services/src/api-push.ts` runs it as `device.register:v1` for the signed-in account, whose row it locks `for update`. It registers or refreshes the installation: under two advisory locks, on the installation and on the token (code design §8, "Lock order"), a row of another installation holding the token is deleted, and the installation's row is written with this account, token and state, and `registered_at` now. So a token or an installation registered under another account moves to this one — the phone changed hands — and the token is never answered or logged. Every call writes: the app sends a fresh `Idempotency-Key` for each attempt, since a replay of an old key could answer for a phone that has moved to another account since, and a replay of the same key and body answers the first result. Each registration counts against the account's 20 writes a minute, so the app registers only when the account, the installation, the token, what the phone allows or its quiet channel changed, or a week has passed.

**Taking it away.** `POST /v1/me/devices/:installationId/remove` takes an empty body (`RemovePushDevice`) and answers 200 with `ApiPushDeviceRemoved`, `{installation_id, removed}`. `removeApiPushDevice` runs it as `device.remove:v1` and deletes the installation only while it is the caller's, in the same statement, so a phone another account has taken over is never removed with it; another account's installation, or one already gone, answers `removed: false` and stays. A path that is no uuid answers 404 before the body is read.

**Both are the account's own.** They name no family, so they take no family middleware and have no 403: an account that was never provisioned, or was deleted, answers 404, as a path that is no installation does; a malformed body or key 400; a key used before with another body 409; no session, or one no longer live, 401 before the database is opened (`apps/worker/src/api-app.test.ts`). A replay answers `Idempotency-Replayed: true` and hands nothing over again. Without the write capability both answer 404, as every write does.

**The founder's alert.** When a registration or a removal takes away a phone that could be told — removed at sign-out, moved to another account, or registered again without permission or with the quiet channel blocked — and that leaves a family the account actively organises with no organiser who can be told, the write inserts `admin.organisers_unreachable` as a queued outbound row in its transaction and hands it to the queue after the commit (`AfterCommit`, § "The quiet notice"), on the first attempt only. That needs push on and the founder's chat: the pilot Worker gives the two routes `writes.alerts` (`ADMIN_CONVERSATION_ID`, `PUBLIC_BASE_URL`, and whether `PUSH_SEND` is `expo`), and while push is off, as now, no device write raises anything, since a phone counts toward nobody being told. `api-dev.ts` records phones and writes no alert.

**One moment a day** is `users.one_moment_a_day` (true unless switched off), read in `GET /v1/me` (`ApiMe.one_moment_a_day`) and written through `PATCH /v1/me` (`ApiAccountPatch`), not through a route of its own. Off stops the account's ordinary pushes, an answer's receipt and the evening's turn prompt, checked when each is written and again when it is sent; it never stops the quiet notice or its close. The hour of the old `/me/notifications` rows (§7) is dropped: an ordinary push goes when there is something to say (spec §5.2, step 6), but never outside 08:00 to 21:00 in the reader's time zone, when it is dropped and what it would have said waits in the app. `GET /v1/me` also says whether this API sends pushes at all (`push`, `PUSH_SEND` `expo`), and `GET /v1/families/:id` tells an organiser how they would be told if her morning went quiet (`told_if_quiet`: `telegram`, an unblocked Telegram link; `app`, push on and a phone of theirs that can be told; null for anyone who is not an organiser), so You can say plainly when nobody would be (principle 7).

**What a push carries.** Its text passes through Expo, Apple and Google and shows on a lock screen, so it holds names and times only — never her words, an answer, a nearby contact, or anything about health — and its data is `PushData`, ids only: `kind`, `family_id`, `member_id` (the kept-light member it is about), and `quiet_event_id`, `exchange_id` or `suggestion_id` where it has one, which the app reads when it is tapped. No title (the app's name shows) and no badge. The pushes built, each made only while push is on (flows §3.4, §3.9, §3.12):

| Kind | To | Text | Held back by |
|---|---|---|---|
| `quiet_notice` | Each active organiser whose live account has a phone that can be told, beside their Telegram notice | `push.quiet_notice`: "It's been quiet at {name}'s today. The morning's message arrived at {sent}. Open Vela to call or wait." | Nothing but the learning period's eight hours, as on Telegram: never budgeted, "One moment a day" and the hour do not apply. Time-sensitive on iOS, Android's loud `quiet` channel, kept for delivery 4 hours |
| `quiet_resolved` | A reader whose app notice of that event was sent, to the account it went to | Telegram's close (`quiet.resolved_answered`, `quiet.resolved_fine`) | As the notice, but not time-sensitive; kept 12 hours |
| `answer_receipt` | Whoever asked the exchange she answered, a person other than her, but not a reader her answer's close has just told | `push.answer_receipt`: "{name} answered you." | The budget (one a day per member, `outbound_budget_idx`), "One moment a day", 08:00 to 21:00; silent, on Android's `daily` channel, kept 12 hours |
| `turn_prompt` | In a family with no Telegram group, the first active organiser, at her 19:00 | `push.turn_prompt`: "Tomorrow morning is yours: ask {name} something." (never the suggestion, whose words can come from hers) | As the answer receipt, with its own place in the budget |

A phone can be told when it is `granted` and, for the quiet notice and its close, has not blocked the `quiet` channel. Not pushed: flags, the weekly read, the widget's refresh, and `delivery.failed`, her stop and the consent answers, which reach organisers on Telegram alone (ADR-34).

**Sending.** A push is one outbound row per reader, on the channel `app`, addressed to their account, and the gateway sends it to every phone of the account that can be told in one request to Expo. It is sent when at least one phone's message was taken, and those tickets are kept (`push_tickets`) in the transaction that marks it sent; dropped, holding no place in the budget, with push off (`push_off`), "One moment a day" off (`one_moment_off`), outside the hours (`quiet_hours`), or no phone that can be told (`no_push_device`, also when Expo says every phone is gone); and otherwise failed and retried as any send is (flows §3.7). `reconcile` reads Apple's and Google's receipts (flows §3.15, step 8). A phone Expo, Apple or Google say is gone is deleted while it still holds the token that push went to, in the transaction that records the send or its receipt, with the founder's alert its loss calls for; Vela's own credentials refused tell the founder once a day (`admin.push_misconfigured`); a quiet notice that reached no phone tells the founder (`admin.quiet_notice_unheard`) unless another notice of that round reached the reader or is on its way, or the round told nobody at all, which `admin.quiet_nobody_told` says instead (flows §3.12, "On phones").

**Where phones go.** A phone is never deleted by age, since an Expo push token does not expire: it goes at sign-out (the route above), when Expo, Apple or Google say it is gone, when its account leaves its last active or paused membership (`leaveApiFamily`; a Leave that keeps another family keeps the phones, which that family's notices need), and when the account is deleted (`disableApiAccount`). A ticket goes once its receipt is read, and by the nightly retention job 2 days after its push.

**Before staging runs it.** Staging's database needs `0005_push` before this code is deployed there, whatever `PUSH_SEND` says, because `GET /v1/me`, Leave, account deletion and the nightly retention read its column and tables (`infra/README.md`, section 9, step 8). Production has neither the migration nor its API on.

### Durable mutation receipts (22 September 2026; served by the pilot Worker, on staging, from 25 September 2026)

`runApiMutation` in `packages/services/src/api-idempotency.ts` provides database-only replay protection. The API's write routes call it, on the pilot Worker and locally; staging's pilot Worker has served them since 25 September 2026. Migration `0001_api_request_receipts` adds the receipt table; apply it before deploying the updated retention job. `0002_account_linking` follows it with `account_link_challenges` and the `account_linked` event name. The applied `0000_init` is unchanged; staging's database has held both migrations since 25 September 2026, and production's holds neither.

- The caller supplies a verified `SessionIdentity`, an opaque key, a server-owned versioned operation identifier, validated JSON input including every write-affecting argument, and optional family/member scopes. `ApiIdempotencyKey` accepts 1–200 ASCII letters, digits, `.`, `_`, `:`, `-`; clients should generate a new unpredictable key per logical mutation. A member scope requires its family. Canonical JSON sorts object keys, preserves array order, rejects non-JSON values and cycles, and bounds nesting to 32 and the complete fingerprint envelope to 16 KiB. The receipt stores SHA-256 hashes of the exact auth subject, key and envelope, not their raw values. Session IDs do not scope the key, so refreshing a session does not repeat a mutation. These hashes are pseudonymous data, not anonymization.
- One transaction first takes the actor advisory lock, then reserves the actor/key pair through its unique constraint, or locks the existing row after a concurrent request completes. The mandatory `authorize(tx)` callback runs after the reservation/lock on every attempt, including replay and conflict, before any saved response is returned. It must perform current account, membership, ownership and consent checks, with locks where concurrent permission changes require them; it must not make business changes. The helper additionally verifies a supplied member belongs to its family.
- For an unexpired receipt, the same fingerprint returns the original saved success result without calling `mutate(tx)`. A different operation, input or scope under that actor/key raises `ApiIdempotencyError` with `conflict`. A committed incomplete or invalid saved result fails closed rather than executing again. If concurrent cleanup leaves no receipt to lock, the helper reports `unavailable` without running the mutation.
- A new or expired receipt runs `mutate(tx)` once, then saves its result in the same transaction. Authorization, mutation, response-validation and receipt-write failures roll everything back. The supported `ApiMutationResponse` is `{status, body}` with status 200, 201, 202 or 204; 204 requires a null body. Saved JSON is limited to 16 KiB and copied before returning. Headers, cookies and error responses are not cached. The replay window is 24 hours from successful completion and is not extended by replay; at expiry the key is treated as a new request, whether or not nightly cleanup has removed its old row. Clients must not rely on deduplication beyond that window.
- Callbacks may write only through the supplied transaction, including durable outbox rows. No external requests or queue sends belong inside the callback: rollback cannot undo them. In particular, the existing `enqueueOutbound` also sends a queue job, so it must not be used as an atomic database-only callback without separating that send. Dispatch happens after commit with the gateway's existing deduplication/redrive rules.
- Under the actor lock, authorized requests also remove expired other receipts for that actor, preserving the current row for expiry reuse. At most 1,000 receipts per actor may remain for a new mutation; excess attempts roll back with `rate_limited` before mutation. Matching unexpired replays remain available at capacity, and other actors are independent. This storage bound is not a gateway request-rate limit: the per-address and per-account admission limits of § "Where the API runs" run before the provider call.
- The nightly retention job deletes receipts whose `expires_at <= now` and records only their count. It selects them `for update skip locked`, so it never waits for a request that holds one: a request reusing an expired receipt holds that row while it deletes the actor's other expired rows, and a job that waited would close a lock cycle, which PostgreSQL breaks by aborting one side, the night's remaining rules or the family's write (found by the contention drill, fixed 23 September 2026). A row a request holds is deleted the next night, inside the same 48-hour window. With healthy nightly execution, physical deletion is within 48 hours of completion; expiry and physical deletion are different. Family/member foreign keys cascade when their scoped rows are physically deleted, ending that receipt's replay retention early; current authorization and scope checks must reject retries for erased resources. Callers must attach the correct scopes for all data returned; mutations that remove their own receipt through a cascade are rejected/rolled back, not silently committed without replay protection.

**Before a write endpoint uses receipts:** wire header/error handling (400 `invalid`, 409 `conflict`, 503 `unavailable`), implement its authorization and ownership proof, and review its exact response fields. Account deletion must purge actor-scoped receipts, and resource-creation/deletion flows must handle associations to newly created resources and deletion of cached personal data explicitly; those lifecycle integrations are not supplied by this generic helper. Never cache session credentials or provider secrets. Signed media URLs, checkout/provider actions and other external effects need endpoint-specific handling, not a claim that this transaction makes them exactly-once. Review/version the public notices before storing live response-cache data; the prospective data-map entry does not change the current pilot notice. PGlite tests exercise replay and rollback, but do not replace an independent multi-connection PostgreSQL contention drill before live writes. That drill now exists as `packages/services/postgres-tests` (code design §8), run with `pnpm --filter @vela/services run test:postgres` against a disposable PostgreSQL 18; on 24 September 2026 it passed whole on 18.6 through local binaries, and through Docker in CI, where the `contention-drill` job now runs it on every push. Its runner had hardcoded vitest's path inside this package's own `node_modules`, where pnpm no longer hoists it: the drill would not start in either the main checkout or a worktree until it was made to resolve vitest instead of guessing, so a drill reported green on 23 September could not be rerun on 24 September at all. It found the deadlock fixed below, and it is the check to rerun when this helper, the linking services, the retention job or the suggestion writer changes; linking's own races are in it too (§"Account linking" above), and since 26 September 2026 the three races of tomorrow's suggestion: one suggestion used by two asks, two writers on one day, and a compose ahead of a writer (§ "Tomorrow's suggestion" above), and the races of photos for an ask: one upload sent twice, one key used for two photos, two uploads for an account's or a family's last place, and a photo ask composed while retention deletes its photo, in both orders (§ "Photos for an ask" above), and since 27 September 2026 those of push: one token registered from two installations at once, a phone handed to another account while its old account signs out or leaves its last family, a receipt saying a phone is gone as the app registers a new token on it, and a send whose phone signs out before its tickets are recorded (§ "Push" above).

### Voices for a reply (2 October 2026, spec §14.1 A8)

`POST /v1/families/:familyId/voice` keeps a recording for a reply, as `POST …/media` keeps a photo for an ask, through the same path (`keepUpload`): the `.m4a` bytes as the body (`Content-Type: audio/mp4`, at most 3 MiB, kept as they came), `Idempotency-Key`, and its length in `X-Duration-Ms`. The object goes under a key minted for the attempt, `replies/<familyId>/<token>.m4a`, then the `media` row (`audio`, no channel, deleted after 30 days) through `runApiMutation` (operation `voice.upload:v1`, fingerprint the SHA-256, size and length), so a retry is answered from the receipt and an attempt's own object is deleted whenever no row names it. It answers 201 `ApiUploadedVoice` (`id`, `kind: "audio"`, `duration_ms`, `bytes`, `expires_at`); 415 `m4a_only` for anything but an MPEG-4 file, 413 past 3 MiB, 429 `voice_limit` past an account's 30 voices in 24 hours (counted under its actor lock, `api-voice-upload-race.test.ts`), 503 where nothing is stored, 404 for a family not the caller's. A reply then names it: `POST /v1/exchanges/:exchangeId/replies` with `{voice: <id>}` writes a reply of kind `voice` naming the recording, which must be the replier's own in her family and still kept, else 404 `voice_missing`. Her next morning reads it back as any voice reply: uploaded to her Telegram chat as a voice message, and played on her phone. Each reply in Today and Exchanges carries `photo`, a photo reply's photo as the ask's photos are given (`ApiExchangePhoto`), null for any other reply. A photo reply works the same way (2 October 2026): the photo is kept by `POST …/media` as a photo for an ask is, and `{photo: <id>}` writes a reply of kind `photo` naming it, which must be the replier's own upload in her family, else 404 `photo_missing`. Her next morning shows it, uploaded to her Telegram chat or on her phone, except beside an ask that shows photos of its own: there it would join the ask's album and her "1" and "2" would no longer name the photos asked, so it is left out and her read-back line still says it was sent.

### Reactions (1 October 2026, spec §6.1, A8)

`POST /v1/exchanges/:exchangeId/replies` also takes `{"reaction": "heart" | "laugh" | "hug"}`: a `replies` row of that kind, no text, channel `app`, `to_recipient` true, under every rule a reply in words follows (her answer first, never her own, the exchange's lock, `reply_posted` with `kind` `reaction`). The receipt's fingerprint is `{exchange_id, reaction}`, so a key spent on a heart cannot be spent on words.

Organisers of her family only; anyone else, and a contact already gone, are 404, since nothing is left to say whose family it was; a retry with the same key replays. Operation `nearby.remove:v1`.


**On Telegram (2 October 2026, ADR-36).** `POST /v1/nearby/:contactId/invite` with `{}`, by an organiser of her family, answers 201 `ApiNearbyInvite` (`contact_id`, `link`): a `t.me` link whose start parameter is `n` and 32 characters, of which only the SHA-256 is kept. Like her phone's set-up, its answer is a credential and is not kept in a receipt: the `Idempotency-Key` is required and unused, and a retry mints a new link that voids the old. 409 `already_listed` for someone who already said yes; 404 for anyone else's contact. The 14 days after which an unanswered contact is deleted run from the latest link. Opening the link in Telegram sends them text B (`nearby-consent.v2`) in that organiser's name with Yes and No; Yes keeps their account with the yes (`ApiNearbyContact.consent` reads `yes`), No deletes them at once, and stop removes them from every list.

`POST /v1/quiet/:quietEventId/ask-to-check` with `{contact_id}` asks one of them to look in, through `runApiMutation` under the event's row lock: 201 `ApiLookInAsk` (`quiet_event_id`, `contact_id`, `asked_at`, `reply`) for the first ask, 200 with the same ask for any repeat that morning, from any organiser; 409 `settled` once the morning closed, 409 `cannot_be_asked` for someone without a Telegram yes, 404 otherwise. `GET /v1/quiet/:id` lists each contact with `phone` (null when they said yes on Telegram), `can_ask`, and `asked` (`at`, `by_name`, `reply`: `yes`, `no` or null).
### Her phone for the parent surface (1 October 2026, ADR-35, phase 1)

`POST /v1/families/:familyId/members/:memberId/device` with `{}`, by an organiser signed in on her phone, sets it up: a new 43-character token, of which only the SHA-256 is kept, on a `channel_links` row of channel `device`; any earlier phone of hers stops working; her `primary_surface` becomes `parent-surface`; event `device_set_up`. It answers 201 `ApiDeviceSetUp` (`member_id`, `token`), once. It is the one write that is **not** kept in a receipt (`runApiMutation`), because a receipt keeps its response to replay it and this response is a credential: the `Idempotency-Key` is required as on every write and is not used, and a retry after a lost answer sets the phone up again with a new token that voids the lost one. Her member row is locked first, so two organisers at once leave one phone, the second's (`api-device-race.test.ts`). Organisers only (403 for anyone else in the family); a member who is not a kept-light member of the family who has not left, invited or not, is 404. Without `writes.devices` the route answers 404.

`POST …/device/remove` with `{}` removes it through `runApiMutation` (operation `device.remove:v1`): the link goes, so the token stops working at once, and `primary_surface` goes back to `telegram` where she has a Telegram link, else `app`; event `device_removed`, only when there was a phone. It answers `ApiDeviceRemoved`.

`GET /v1/device` with `Authorization: Device <token>` answers `ApiDeviceMember` (`member_id`, `display_name`, `address_form`, `language`, `status`): who her phone is, before anything else is read. A token that is not 43 characters of base64url, is unknown, was replaced or removed, or is hers after she left, and a request with a Bearer session or with no `Authorization`, are 401 alike. Her phone is a chat (phase 3, 1 October 2026): `GET /v1/device/messages` answers `ApiDeviceMessages`, the latest ten messages Vela sent her `device` link, newest first, each with `message_id`, `kind` (`consent`, `arrival`, …), `exchange_id`, `text` and `buttons` as they were sent, `photos`, the ids of its photos in order, and `voices`, the ids of the family's voice notes it reads back; a row whose payload retention cleared is left out. Her morning names each of its photos and voice notes by the storage key of Vela's own copy: a file only Telegram holds is fetched and stored under its row's id first (`storedCopyOf`), and one Telegram can no longer give is left out, so a photo choice short of its second photo goes to her as a question (2 October 2026). `GET /v1/device/media/:mediaId` with her device token answers a photo's or voice note's bytes with the type it was stored as (`image/jpeg`, `image/png`, `image/webp`, `audio/ogg`, `audio/mpeg`, `audio/mp4`), uncached, for the photos any member of her family may see (`sharedWith`: one an exchange, answer or reply of the family carries); 404 for any other id, an id that is not a uuid, and wherever photos are not kept; 401 as her other routes. The gateway loads no bytes to send her phone a photo. What she says goes to the pilot Worker, beside the Telegram webhook, not under `/v1`: `POST /device/messages` with `Authorization: Device <token>` and `DeviceInput`, a tap `{button, message_id}`, words `{text}` (1 to 4,000 characters), or her voice `{voice}` (2 October 2026), the media id of a recording of hers uploaded first. Her token is checked against the database, then her input becomes the inbound event a Telegram chat would make of it (`deviceInboundEvent`: channel `device`, she the sender and her phone the private conversation, both named by her link) and goes through `handleInbound`, so her consent, her answers, stop and start are the router's own. It answers 200 `{ok: true}`, 400 for a body that is not the contract's or a voice naming no recording of hers, and 401 for a token it does not know. A voice is the router's voice note, named by its recording (event and message id `voice:<media id>`), so sending it again is never a second answer; the pipeline reads its stored copy for the transcript. `POST /device/voice`, also on the pilot Worker with her device token, takes her recording before it is sent: the `.m4a` bytes as the body (`Content-Type: audio/mp4`, at most 3 MiB), a key of 8 to 64 characters of `A–Z a–z 0–9 _ -` that names the recording in `Idempotency-Key`, and its length in `X-Duration-Ms`. It keeps the file as a `device` audio row of hers and answers 201 `{media_id}`, the same id for the same key, also when a retry reaches it while the first is still writing (`device-voice-race.test.ts`); 400 for anything that is not an MPEG-4 file or a bad key, 413 past 3 MiB, 429 past 30 recordings in 24 hours, 404 where nothing is stored. What she says on her phone is posted to the family's Telegram group, her phone having no group of its own, her voice as an upload of its stored copy, and a flag in it is told to the organisers on Telegram. A phone set up before her yes is sent the consent request a Telegram chat gets when she opens her invite (`consentRequestMessage`), handed to the queue after the set-up commits.

## 11. Core types (Zod, `packages/contracts`)

**Implemented foundation, 21 September 2026 (build plan 2.1, partial).** `packages/contracts/src/api.ts`, exported from the package root, provides `ApiErrorCode` and `ApiErrorBody` (the envelope in the conventions, with optional JSON-object `details`), `PageQuery`, `MemberLight`, `SetLight` (`{on: boolean}`), and `PauseMember` (`{paused: boolean}`), with inferred TypeScript types. The account/read slice in §1 additionally implements `ApiAccountProfile`, `ApiAccountPatch`, `ApiUser`, `ApiMe` and `ApiFamilyPlan`, the mutation plumbing `ApiIdempotencyKey` and `ApiMutationResponse`, and the linking shapes `ApiLinkChallenge`, `ApiLinkCode` and `ApiLinkOutcome`. Push (27 September 2026, §1 "Push") adds `ExpoPushToken`, `RegisterPushDevice`, `ApiPushDevice`, `RemovePushDevice`, `ApiPushDeviceRemoved` and `PushData`, and to the domain `PUSH_PLATFORMS`, `PUSH_PERMISSIONS`, `ORDINARY_PUSH_KINDS`, `PUSH_EXCEPTION_KINDS` and `PUSH_KINDS`. These schemas alone expose no HTTP route and perform no authentication, membership, consent, or idempotency checks; the service and Worker boundaries enforce access separately. The remaining request/response shapes below are design sketches, not implemented exports.

`PageQuery` accepts HTTP query strings: optional nonempty opaque `cursor` and optional digits-only `limit`, parsed into a positive safe integer (`PageQueryInput` is the string-valued input type; `PageQuery` is the parsed type). Empty, fractional, signed, exponential and unsafe limits are rejected, as are unknown query fields. Omitted fields stay absent: endpoint-specific defaults, maximum page sizes, cursor encoding and cursor scoping must be implemented before any list route is exposed. The light and pause request bodies are strict and accept actual JSON booleans only. Response schemas strip undeclared fields; they do not sanitise text or error details, which callers must populate with deliberately public values only. `MemberLight` reuses the domain's `LightState`, `LocalDate` and `LocalTime`: usual time is `HH:MM`, dates must exist, timestamps include `Z` or a numeric offset, and nullable fields must be present explicitly.

## 12. Channel adapter contract (worker-internal)

```ts
export interface ChannelAdapter {
  readonly id: "line" | "whatsapp" | "telegram" | "voice" | "app";
  readonly capabilities: { buttons: boolean; voiceIn: boolean; voiceOut: boolean; readReceipts: boolean; images: boolean; templatesOutsideWindow: boolean };
  // must be idempotent on msg.idempotencyKey; files: the bytes of each media item named only by a
  // storageKey, keyed by that key, loaded by the gateway for this attempt (ADR-33)
  send(msg: OutboundMessage, files?: ReadonlyMap<string, FetchedMedia>): Promise<{ externalId: string }>;
  verify(req: Request): Promise<boolean>;
  parse(req: Request): Promise<InboundEvent[]>;
  resolveIdentity(ev: InboundEvent): Promise<ChannelLink | null>;
}
export type OutboundMessage = {
  kind: "arrival" | "repeat" | "ack" | "consent" | "nearby_ask" | "system";
  text: string; lang: Lang; media?: OutboundMediaRef[]; voice?: MediaRef; buttons?: { id: string; label: string }[];
  idempotencyKey: string; exchangeId?: string;
};
// A file an outbound message carries: one the platform holds (providerFileId), one it can fetch
// (url), or one Vela keeps (storageKey), at least one of the three. Inbound events use MediaRef,
// which has no storageKey.
export type OutboundMediaRef = {
  kind: "audio" | "image"; providerFileId?: string; providerUniqueId?: string; url?: string;
  storageKey?: string; mime?: string; durationMs?: number; bytes?: number;
};
export type FetchedMedia = { body: ArrayBuffer; mime: string };
export type InboundEvent = {
  channel: ChannelAdapter["id"]; externalUserId: string; externalMessageId: string; at: string;
  kind: "text" | "voice" | "image" | "sticker" | "button" | "reaction" | "read" | "follow" | "unfollow" | "blocked" | "dtmf";
  payload: { text?: string; buttonId?: string; mediaUrl?: string; mime?: string; durationMs?: number; reaction?: string; digit?: string };
};
```

**Stored files (26 September 2026, ADR-33).** As built in `packages/contracts/src/adapter.ts`, `ChannelAdapter.send(message, files?)` takes the message, whose `to` names the conversation, and the bytes of every `media` item that has a `storageKey` and neither a `providerFileId` nor a `url`, keyed by that key. `OutboundMessage.media` is `OutboundMediaRef[]`, a schema of its own, so `MediaRef`, which inbound events carry, stays without a storage key and its check still asks for a file id or a URL. The gateway loads the files on each attempt (`loadOutboundFiles`), so a retry reads them again and the outbound row keeps only the key; an adapter that is handed a stored item without its bytes refuses it (`ChannelSendError` `invalid_request`) rather than sending the message short of a file. The Telegram adapter uploads stored photos as multipart/form-data (§1 "Photos for an ask") and refuses a stored audio item (`invalid_request`); none is ever built, since an arrival names a voice only by the file id Telegram gave it and leaves out one it has no file id for.

**The app's channel has no adapter (27 September 2026, ADR-34).** `app` is a `Channel`, and an outbound row on it is a push to the reader's phones, but `ChannelRegistry.get("app")` stays unwired: the gateway sends such a row through services' push port (`Deps.push`, Expo's push service; code design §6 and §8), which adapters never touch, since they never touch the database and the row must first be fanned out to the account's phones. No inbound event arrives on it.

Deviations recorded per adapter in `architecture/02-technical-architecture-v2.md` §6.
