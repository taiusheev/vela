# Release runbook

Updated 5 October 2026 · architecture §16–17 · code design §9–10 · ADR-23, ADR-26, ADR-42 · engineering prepares, the founder approves production

## When to use it

Every change to either Worker in staging or production, every database migration and each signed trial app build. The active release scope is the English-only Telegram/iPhone cohort in [`english-trial-readiness.md`](../../plan/english-trial-readiness.md): seven own-family days in Vietnam after eligibility review, then 30 days with 3–5 approved Taiwan families. A green source check or staging heartbeat is not authority to activate a real family.

The app currently has no configured EAS Update runtime/channels. Trial app fixes require a new signed build. [`ota-policy.md`](ota-policy.md) remains the policy for a future verified setup; the native Opus decoder, permission or entitlement changes always require a native build and appropriate review.

Each environment has two Workers, deployed from `apps/worker` (`architecture/decisions.md`, ADR-26): the pilot Worker `vela` (`apps/worker/wrangler.jsonc`: the webhook, the privacy notice pages, the scheduler, the queues and cron) and the admin Worker `vela-admin` (`apps/worker/wrangler.admin.jsonc`: the admin pages, behind Cloudflare Access). Staging's are in the "Vela staging" account, at `https://vela.vela-light-staging.workers.dev` and `https://vela-admin.vela-light-staging.workers.dev`; production's are in the "Vela" account, at `https://vela.vela-light.workers.dev` and `https://vela-admin.vela-light.workers.dev`. `.github/workflows/deploy.yml` deploys both, the pilot Worker first, because the admin Worker binds the `MemberScheduler` class it exports.

## Before an environment's first deploy

An environment's first migration and deploy are not done with this runbook: the founder runs the setup script once for it, `pnpm --filter @vela/worker run setup -- --env staging`, then, once staging has passed, `--env production` ([`infra/README.md`](../README.md), sections 11 and 12). The script creates the queues and the dead-letter queue with the names in `wrangler.jsonc`, and the R2 media bucket only where that environment's `MEDIA_STORAGE` is `r2`, which is staging (`vela-media-staging`, since 26 September 2026) and production (`vela-media-production`) today (decision M of 20 September 2026, [`infra/README.md`](../README.md), section 1, step 3); migrates the database; replaces every `PLACEHOLDER_` value for that environment (the bot username in `wrangler.jsonc`, the Hyperdrive id in both wrangler files), which the co-founder then commits; puts each Worker's secrets (`ADMIN_CONVERSATION_ID` among `vela`'s; `ACCESS_TEAM_DOMAIN`, `ACCESS_AUD` and `ANTHROPIC_API_KEY` on `vela-admin`); deploys `vela`, then `vela-admin`; waits while the founder has Cloudflare Access protect the whole `vela-admin` Worker and nothing else; registers the Telegram webhook; and checks the result. Before it, the GitHub environment holds `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID` and `DATABASE_URL`, which every later deploy needs. Both privacy notices in `plan/materials/pilot` were filled in on 17 September 2026; after any later edit, `apps/worker/src/notices.generated.ts` is regenerated in the same commit. The pilot Worker refuses to run while any value still holds `PLACEHOLDER_`, a URL var is not https, a secret is missing, or a notice holds a bracketed blank, so a pilot Worker deployed like that answers the notice pages once both notices are filled, but handles no webhook update, queue job, cron run, or alarm, and its `/healthz` never answers `ok`, because no reconcile finishes; a deploy whose queue or bucket does not exist fails. After an environment's first deploy passes its checks and `/healthz` there answers `ok`, the co-founder sets that environment's `enabled` to `true` in `.github/watchdog.json` and commits it, so the watchdog starts reading it (`infra/README.md`, section 6).

## Rules

- Trunk-based. `main` is always deployable; `pnpm check` passes before every merge.
- GitHub metadata rechecked 5 October 2026: `staging` permits branch `main` only; `production` permits `v*` tags only and requires reviewer `taiusheev`. Self-review is permitted for this sole founder account. `main` now requires strict current-head checks named `lint · typecheck · test`, `contention drill (PostgreSQL 18)` and `app flows (Maestro, demo on the web)`, including administrators; force pushes and deletion are disabled. There is no additional pull-request reviewer requirement. Verify these controls and the candidate's actual green runs before merging.
- `main` deploys to staging. Production deploys only from a `v*` tag, through CI, after the founder approves the `production` environment in GitHub. Never `wrangler deploy --env production` from a laptop, with one exception: the founder's own run of `pnpm --filter @vela/worker run setup -- --env production`, once, before any family, with a setup token that expires the next day and is deleted after the run (`infra/README.md`, access rules and section 11).
- Production deployment and the trial app workflow fetch the tag's history, require its SHA to be an ancestor of `origin/main`, and query GitHub for the latest successful completed non-nightly `ci` run on that exact SHA before releasing it. They have read-only Actions access for that check. A green run from another commit, an unfinished/failed newer run or a nightly-only run cannot establish a tested release tag.
- **Migrations expand, then contract.** A migration must work with the code already in production, because the migration runs first and the code follows. Adding tables, columns or indexes is one release; renaming or dropping takes two (stop using it, then remove it).
- **Never rename or remove the `MemberScheduler` Durable Object class** without a planned Wrangler migration: removing the class deletes every member's alarms and stored wake times. **Never rename the pilot Worker `vela`** either: the admin Worker reaches the class by that name (`script_name`).
- **Never turn on Cloudflare Access for `vela`**, or for all Workers in the account: Telegram's webhook and the privacy notice pages must answer without a sign-in. Access belongs on `vela-admin` only.
- **Timing.** Deploy when no family's arrival hour falls in the next 30 minutes (the admin page lists the next arrivals). If the change touches turn prompts or preparation, also avoid 19:00–22:00 in any family's zone.
- A change to consent, notice or agreement wording follows the versioning rules in `plan/materials/pilot/README.md`.
- Domain purchases, provider accounts/billing, Apple membership/signing, private secret entry, participant approval and production approval belong to the founder. Engineering prepares the concrete changes and verifies nonsecret status/identifiers; it never handles production credentials or family content. Environment protections do not create or validate their secrets.

## Steps

1. **Pull request.** CI green on the candidate commit: lint/typecheck/tests, real PostgreSQL 18 contention and app flows. New behaviour has a relevant regression check; a migration's SQL is read in the diff. English app catalogs must match source and pass strict ICU checks. Other catalogs keep synchronized keys, but new English-only strings may remain untranslated for this cohort. Chinese completeness/style/native review remains an open future gate, run explicitly with `pnpm --filter @vela/app test:i18n:future` before enabling those locales. Web demo flows must explicitly set `EXPO_PUBLIC_DEMO_MODE=true` with API/auth configuration absent; they prove no signed-in or native behaviour.
2. **Merge.** CI (the GitHub `staging` environment) runs the checks, applies migrations to staging's own Neon project, `vela-staging`, once, then deploys `vela`, then `vela-admin`. Until the `staging` environment holds its secrets, these steps are done by hand, in this order. The co-founder never holds the staging connection string (`infra/README.md`, rule zero), so a migration is run by the founder, in their own terminal on the tested commit, pasting `vela-staging`'s direct string from the password manager at the hidden prompt:

   ```bash
   read -rsp "Staging connection string: " DATABASE_URL; echo; export DATABASE_URL
   VELA_DATABASE_ENVIRONMENT=staging pnpm --filter @vela/db migrate
   unset DATABASE_URL
   ```

   It prints "Migrations from … applied." The explicit environment is a nonsecret instruction, separate from the pasted connection. Both CI jobs supply it as a literal value. Migration and resealing refuse remote connections outside that environment's verified host/database/role/TLS target before creating a client, and reject driver overrides or inherited `PGOPTIONS`. Local development remains available on loopback hosts and its explicit port. Then the co-founder deploys both Workers with the "Vela staging" token in `apps/worker/.env`, which Wrangler reads when it runs in `apps/worker` (`infra/README.md`, section 1, step 8), the pilot Worker first:

   ```bash
   pnpm --filter @vela/worker exec wrangler deploy --env staging
   pnpm --filter @vela/worker exec wrangler deploy -c wrangler.admin.jsonc --env staging
   ```

3. **Staging smoke test (15 minutes).**
   - `https://vela.vela-light-staging.workers.dev/healthz` returns 200 with `"status":"ok"` (within 15 minutes of the deploy, once a reconcile has run); `/privacy` and `/privacy/zh-TW` on that host open with no sign-in; `/admin` on that host answers `not found`; and `https://vela-admin.vela-light-staging.workers.dev/admin` opens through Cloudflare Access. `/healthz` builds no deps and never touches the database: it answers `ok` only while a reconcile has finished in the last 35 minutes, which needs the pilot Worker's configuration, its database and its cron, so it proves the pilot Worker, and the admin page proves the admin Worker's configuration.
   - In the staging family group, reply to the turn prompt with an ask; the bot answers "Into [name]'s morning."
   - **Arrival**, only if the staging test member has had no arrival delivered today (the scheduler delivers one per local day; a second release the same day, or a release after the morning's arrival, skips this line and says so in the release notes). The founder sets the arrival at least 30 minutes ahead and clears the stored wake, in the Neon console in the project `vela-staging`, as in [`silence-drill.md`](silence-drill.md), "Setting the arrival hour H" (editing `arrival_time` alone leaves the old alarm in place). The arrival comes once at that time; tap an answer; the light line appears in the group.
   - Both Workers' logs in the "Vela staging" dashboard show, since the deploy, no line whose `level` is `error` (such as `request_failed`, `queue_job_failed`, `cron_failed`, `scheduler_tick_failed`, `reconcile_tick_failed`, `outbound_failed`, `outbound_redrive_failed`), no `ConfigError`, and no uncaught exception. Sentry is not connected to either Worker yet (`SENTRY_DSN` is not read) and stays empty whatever fails, so these logs are the error check.
   - If the scheduler, gateway, quiet ladder or an adapter changed: run the staging silence drill ([`silence-drill.md`](silence-drill.md)).
   - For an English trial candidate, also exercise pilot admission, organiser/contributor proof-code linking and a genuine app ask → Telegram arrival → text/photo/Ogg answer → app display → human reply → next-morning read-back, using synthetic accounts/content. Exercise expired codes, failed writes, retry identifiers, AI-off/failure and health-consent withdrawal. Record exact scheduled/delivered/failed counts. The public `/v1/capabilities` endpoint reports configuration only; it is not a membership, scheduler or media playback test.
4. **Tag.** The founder opens **GitHub → Releases → Draft a new release**, creates the tag `vYYYY.MM.DD` on the tested commit (add `.2` for a second release the same day), writes two lines (what changed; migration yes or no) and publishes.
5. **Approve.** The production job waits for the founder's approval of the `production` environment. Approve it.
6. **CI** (the GitHub `production` environment, the only place the production connection string and Cloudflare token exist) runs the checks, applies migrations to the Neon project `vela` once, then deploys `vela`, then `vela-admin`.
7. **Watch for 30 minutes.** `https://vela.vela-light.workers.dev/healthz` 200 with `"status":"ok"` and its `/privacy` pages open; `https://vela-admin.vela-light.workers.dev/admin` opens through Cloudflare Access; both Workers' logs in the "Vela" dashboard show, since the deploy, no line whose `level` is `error`, no `ConfigError`, and no uncaught exception (as in step 3; Sentry is not connected yet); no watchdog failure email; the next due arrivals delivered on time in the admin page; no `scheduler_missed`; dead-letter queues empty.

## English trial app release

1. **Private setup and release hold.** Follow the production handoff in [`english-trial-readiness.md`](../../plan/english-trial-readiness.md). The checked-in production `API_V1` is still `off`; a successful Worker deploy alone does not enable the app. The founder approves an owned Clerk domain and its account setup, production issuer and `sk_live_` installation, production resources/recovery, private pilot roster, Apple membership/signing and TestFlight review. Engineering prepares the reviewed configuration, notice/module changes and evidence. Keep real-family activation on hold while any applicable gate is open.
2. **Capability check.** Enable the production API only through the reviewed configuration change and its own evidence. `GET /v1/capabilities` must return `pilot=true`, `telegram_first=true`, `english_only=true`, `memory=false`, `book=false`, `parent_app=false`, `billing=false`. `BOOK` stays off for the real-family trial, deferring new long-term story retention; genuine existing story records remain readable. Free weekly reads stay enabled. Parent Telegram consent is independent of app linking, and an organiser private notification must have been successfully delivered before parent activation. Stop/privacy/deletion remain available after roster removal.
3. **Build the same tested source.** In GitHub **Actions → app build → Run workflow**, select the tested main-derived `v*` tag, profile **trial**, platform **ios**. The workflow uses the protected production environment, verifies main ancestry and exact-SHA non-nightly CI, tag/iOS/`pk_live_` shape and production capability flags, then runs `pnpm check`. The trial EAS profile targets the production API/environment, sets `EXPO_PUBLIC_TRIAL_ENGLISH=true` and increments the build number. `app.config.ts` rejects a staging API or development Clerk key, disables tablets and writes `extra.trial` and `extra.releaseCommit`. The founder enters the production publishable key in the EAS production environment and matching protected GitHub environment; this public key is an identifier, while Apple credentials and secret keys remain private. Non-trial **staging/e2e/testflight** workflow runs use the main-only staging environment. **testflight** inherits staging authentication and is not the real-family trial build.
4. **Follow EAS and Apple.** The GitHub workflow uses `eas build --auto-submit --no-wait`; its green result confirms the handoff only. Record the completed EAS build ID, iOS build number, App Store Connect/TestFlight processing result and embedded source commit. Prepare English review information, a usable synthetic reviewer account/link flow, privacy/support URL and microphone/photo explanations. Confirm required external TestFlight review before inviting friends; an upload or submission is not approval.
5. **Native/device proof.** Expo Go lacks `VelaOpusDecoder`. The pinned local C host tests and Apple autolinking checks do not compile the Swift module or establish CocoaPods/device integration. Build for simulator and signed iPhone, then test real Telegram Ogg/Opus, app M4A and MP3, pause/replay, cancellation, expiry, deletion, foreground/background, failed download, microphone/photos denial, VoiceOver/large text, offline saved-text retry, sign-out and a second account on the same phone. Record device/iOS/build/commit and exact outcomes. The local decoder accepts at most 20 MiB and five minutes; explain an unsupported recording without fabricated playback success. No host-only receipt can close this gate.
6. **Activate in order.** Record eligibility/provider/consent review and actual Vietnam phone/network checks first. The founder approves each adult; engineering installs the private Telegram roster without exposing it. Complete organiser/group setup and confirmed private delivery, connect the existing family in the app, then let the parent answer their own consent/health questions. Complete the seven-day own-family week before the Taiwan expansion. Code readiness, operational readiness and the observed family week are separate records.

The release record contains the candidate SHA, green CI run, PostgreSQL receipt, deployment tag/Worker versions, capability snapshot, completed signed build and embedded commit, device outcomes, recovery/alert evidence, eligibility/notice versions and founder approval. Record counts and content-free outcomes; never store credentials or real family quotes in this runbook. Source-check receipts are appended only once the actual candidate passes.

## Provider and account lifecycle proof

Staging's AI provider remains `off` in both Worker configurations. Secret-name metadata checked 5 October found no `ANTHROPIC_API_KEY`, `PILOT_TELEGRAM_ALLOWLIST` or `CLERK_WEBHOOK_SIGNING_SECRET`. The founder completes the private Anthropic account/credit/key setup before engineering flips both provider configurations in a reviewed change. Then run authorised synthetic live-provider cases, including health permission and provider failure. Off-provider/fake-provider tests remain useful fallback evidence, never proof that live AI has run.

In each used Clerk instance, the founder configures a webhook endpoint on that environment's public `vela` Worker at `/webhooks/clerk`, subscribing initially to **user.deleted**, and privately installs the endpoint-specific **CLERK_WEBHOOK_SIGNING_SECRET**. It is a Svix `whsec_` key, separate from Clerk's API key, and belongs to `vela` only. Keep the endpoint outside Cloudflare Access; signature verification supplies authentication. Confirm the instance, destination/environment and secret installation without exposing the key, body or signature in logs or notes.

Before real-family activation, delete a synthetic Clerk account through the provider, confirm the signed delivery succeeded, and verify old API reads, writes, link challenges and replay receipts are refused. The handler accepts only a bounded raw body and a five-minute signature timestamp window; missing/invalid signing configuration fails closed. Repeated **user.deleted** creates the same permanent account-access tombstone and removes its receipts/link challenges/push devices. **user.updated** and other events are acknowledged but ignored; reversible bans/locks are not permanent deletion evidence. This revokes app account access and does not delete shared family content, which still follows the consent/data-request procedures. Source signature/race tests and a manually forged request cannot close the actual Clerk delivery gate.

## Rollback

- **Code:** in the "Vela" account's Cloudflare dashboard, go to the **Workers & Pages** page, select the Worker (`vela`, `vela-admin`, or each in turn when the release changed both) **→ Deployments**, select the three dot icon on the right of the previous version, and select **Rollback**. Nobody runs `wrangler rollback` against production from a laptop, which holds no production credential (the production setup token is deleted after its one run). This reverts code only; secrets, the queues and the database stay as they are, which is why migrations expand before they contract. Cloudflare refuses a rollback across a Durable Object migration (a change to the `MemberScheduler` class, or the migration that adds the heartbeat's `ReconcileHeartbeat` class, ADR-18 update of 18 September 2026), or to a version whose bucket or queue no longer exists.
- **A migration damaged data:** Sev 1 in [`incident.md`](incident.md), then "Doing it for real" in [`restore-drill.md`](restore-drill.md).
- After any rollback, add it to the incident note and fix forward through this runbook.

## How to know it worked

For a Worker release: the CI production job is green; each Worker's version in the Cloudflare dashboard matches the tag; the smoke test passed; the 30-minute watch was clean; and the next eligible arrival is delivered on time. For trial activation, every applicable readiness gate also has evidence, the signed iPhone build matches the tested commit and the actual family loop has been observed. None of those results is inferred from `/healthz`, a capability response, a host decoder test or an EAS handoff.
